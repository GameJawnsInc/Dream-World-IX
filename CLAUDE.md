## 1. What this project is now

It began as "add one playable custom room to FF9 (Steam, Memoria engine)." **That is long done.** It is now **`ff9mapkit`**: a Python toolkit + Blender add-on that compiles a declarative **`field.toml`** into a complete drop-in Memoria mod â€” a brand-new FF9 field (camera, walkmesh, painted art, NPCs, dialogue, gateways, encounters, events, story branching, cutscenes, ladders, jumps, props, save points) â€” and can **import/fork any of FF9's ~674 real fields** faithfully. Further pillars: battles, campaigns/journeys, playable characters, custom models, custom overworld, items/equipment/shops.

**North star â€” fork FIDELITY:** keep refining forked fields until the kit can recreate the *functioning game itself* from them ("fork a real field â†’ does it play identically?"). The *physical* layer (scene/walkmesh/camera/mechanics/object-carry) is largely faithful + in-game proven; the *narrative-state* layer is the weak axis (a fork boots at scenario-zero). Honest gap map: **`ff9mapkit/docs/FORK_FIDELITY.md`**. Code lives at `ff9mapkit/` (package `ff9mapkit/ff9mapkit/`, Blender add-on `ff9mapkit/blender/`); the dev-loop tools at repo-root `tools/`.

## 4. The dev loop (no relaunch needed)

The proven fast loop â€” **edit â†’ deploy â†’ ~**:

1. Author/edit a `field.toml` (by hand, the form editor, or a Blender export).
2. `py tools/deploy_field.py <field.toml> [--id N]` â€” builds + deploys reversibly into the test slot (default 4003 = `TESTROOM`); reverts the slot's prior deploy; writes a per-id `revert_deploy_<id>.py`.
3. In-game press **~ â†’ Reload field** (re-reads the field's mod files from disk) **or â†’ Warp to field â†’ <id>**.
4. Ask the human to verify. Each change = one commit + one in-game check.

**Relaunch is only needed for:** the FIRST deploy of a *new* id (registers its DictionaryPatch line), a BattlePatch change, or an engine-DLL rebuild. Revert: `py tools/scroll_out/revert_deploy.py` (latest) or `revert_deploy_<id>.py`.
Text-block/`.mes` shadowing across stacked folders (wrong text, right flags) â†’ the `deploying-ff9-mods` skill, [[project-ff9-text-block-shadow]]. Engine DLL builds (**AUTO-DEPLOY, no backup â€” DANGEROUS**) â†’ the `building-the-memoria-engine` skill, [[project-ff9-memoria-build]].

## 8. Dead ends (proven â€” don't re-explore)

- **HW "Export as Custom Field" atlas clone** â€” systemic UV bug (A/B tested on two bases). Use
  BG-borrow or `--editable` custom scenes instead.
- **HW adding a new `.eb` entry** â€” corrupts the file (overwrites the player object). Python only.
- **The FieldCreator editor's 5-point camera anchor on a flat floor** â€” mathematically degenerate.
- **Encoding a field warp as opcode `0x2A`** â€” that's `Battle`, not PreloadField â†’ crash/black.
- **A uniform `orgPos/2` walkmesh slide / an `f0`-vs-`+org` frame auto-detector** â€” the import
  frame is always `vert + orgPos + floor.org`; no heuristic.
- **Per-pitch `sx/sy` canvas scale** â€” the map is exact scale-1; the "back-edge drift" was the
  character collision radius, not a map error.
- **Grafting a render-only NPC's talk handler into a NON-verbatim fork (#14)** â€” proven 0-tractable (census of
  675 fields: an NPC's interactive tag-3 IS the field's quest logic, inseparable). Use **`--verbatim`**; read
  what an NPC does with **`fork-report --explain`**. (Adding NEW *self-contained* kit content to a *verbatim*
  fork IS supported â€” a different problem â†’ [[project-ff9-npc-on-verbatim]].)
