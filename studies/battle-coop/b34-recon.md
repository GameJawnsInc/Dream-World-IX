## UNITMAP — verdict: CONFIRMED

### The verified answer

UNIT MAPPING — the wire Index IS the btl_data array slot; resolve by direct array access with a four-guard predicate, never by list enumeration.

(a) WHAT GetIndex IS. `BattleUnit.GetIndex()` is log2 of `Data.btl_id` (`while (1 << index != Data.btl_id) ++index;` — BattleUnit.cs:627-635). It is NOT `bi.line_no` (that is the separate `Position => Data.bi.line_no`, BattleUnit.cs:50). Assignment:
- PLAYERS: `btl_init.InitPlayerData` walks `party.member[0..3]`, skipping nulls, taking `btl = btlsys.btl_data[btlIndex]` with a COMPACTED btlIndex, and calls `OrganizePlayerData(player, btl, (UInt16)memberIndex, (UInt16)btlIndex)` (btl_init.cs:260-287). Inside, `btl.btl_id = (UInt16)(1 << btl_no)` (btl_no = compacted btlIndex, :374) and `btl.bi.line_no = (Byte)cnt` (cnt = RAW memberIndex, :380). So for players GetIndex = compacted party position = btl_data slot 0-3, and line_no = the raw slot; they differ when a mid-array null exists.
- ENEMIES: `btl_init.InitEnemyData` iterates `PatAddr[PatNum].Monster[enemyIndex]` for enemyIndex 0..MonsterCount-1 into `btl_data[4+enemyIndex]`, assigning `monBtl.btl_id = (UInt16)(16 << enemyIndex)` = 1 << (4+enemyIndex) and `bi.line_no = 4 + enemyIndex` (btl_init.cs:37-63). Slave parts (GetMonGeoID < 0, multi-part bosses) still receive their btl_id in sequence (:49-60). Unused slots get `btl_id = 0` (:89-93).
INVARIANT: for every live unit, GetIndex == its btl_data array slot i, and btl_id == 1 << i, players 0-3 / enemies 4-7. Nothing ever reassigns btl_id mid-battle (`btl_id = ` census: only btl_init init sites + SFX.cs:1725, which runs only under `SFX.isDebugMode` — set solely by the SpecialEffectDebugRoom scene, SFX.cs:1644-1652, never in the diorama).

(b) 1:1 CORRESPONDENCE — YES, with two provisos. Enemy order is fully deterministic from scene bytes: PatNum on the guest is exactly the wire pattern (`PatNum = isDebug ? patternIndex : ChoicePattern()`, HonoluluBattleMain.cs:206), and InitEnemyData/PutMonster/SetMonsterData contain no RNG on the identity/order path (RNG only touches starting ATB `cur.at = random16() % max.at`, OrganizeEnemyData btl_init.cs:500, and idle animFrame :524 — both cosmetic, and the reconciler overwrites ATB). Player indexes are the COMPACTED party positions, not raw slots; correspondence holds because `NetSyncDiorama.MirrorHostParty` mirrors party.member SLOT-EXACT including nulls (`if (!s.Present) ff9.party.member[i] = null`, NetSyncDiorama.cs:383-386). PROVISO 1: the unseatable-character fallback (`no such character on this install; slot left empty`, NetSyncDiorama.cs:393-397) nulls a mid-array slot and SHIFTS guest compaction — silent player mismap unless guarded (see (c) guard 4). PROVISO 2: identical battle-scene bytes on both machines is a data assumption, not provable from source.

(c) RESOLUTION CODE (guest, every apply tick — resolve fresh, never cache BTL_DATA):

Do NOT use `EnumerateBattleUnits()` — it walks btl_list (FF9StateBattleSystem.cs:111-115), and units are UNLINKED from btl_list while still being real: dead enemies at die_seq 5 (`btl_sys.DelCharacter(btl)`, btl_mot.cs:350), removed/snorted players (`BattleUnit.Remove` → DelCharacter, BattleUnit.cs:574-583), and script-hidden units (SV_FunctionEnemy[33] → DelCharacter, btl_scrp.cs:436). `EnumerateDeletedUnits` (FF9StateBattleSystem.cs:123-131) exists precisely because unlinked-but-live is a normal state. ## HPMP — verdict: CORRECTED

### The verified answer

RECOMMENDED WRITE PATH — the LOGICAL property pair, max-before-cur, with death driven by the Alive lane, plus two new containment lines that the hp=0 case makes mandatory.

Per 150 ms tick, per resolved unit (btl_scrp.FindBattleUnit(1<<hostIndex) or matching GetIndex):

1. `unit.MaximumHp = wire.HpMax; unit.MaximumMp = wire.MpMax;`  (write max FIRST — the per-frame clamp in btl_para.CheckPointData clamps Current to Maximum, so cur written before max can be eaten for one frame)
2. If `wire.Alive`:
   - if `btl_stat.CheckStatus(unit, BattleStatus.Death)` → `btl_stat.RemoveStatus(unit, BattleStatusId.Death)` first (writing CurrentHp>0 does NOT clear Death — nothing in the engine un-kills on hp>0; DeathStatusScript.Remove resets die_seq/death_f/stop_anim, which is exactly the revive bookkeeping)
   - `unit.CurrentHp = wire.HpCur; unit.CurrentMp = wire.MpCur;`
3. If `!wire.Alive`: write RAW `unit.Data.cur.hp = 0` (deliberately bypassing SetLogicalHP's non-dying-boss floors — the host has authoritatively declared death, and the floors would turn 0 into 1 and the actor would never die) and let the stock frame loop do the rest: BattleMainLoop → CheckPointData sees raw cur.hp==0 → AlterStatus(Death) (bypassResistances is true when cur.hp==0) → CheckStatusLoop → DieSequence → pose/fade. Do NOT encode death as HpCur==0 through the logical setter.

SetLogicalHP is otherwise the right cur-HP write: it is a near-pure field write (no max clamp, no kill, no event), and it is the exact inverse of the host's sampling transform (GetLogicalHP) whenever host and guest agree on Configuration.Battle.CustomBattleFlagsMeaning and on the enemy's ENEMY_INFO.flags. CurrentMp/MaximumMp are raw passthroughs (BattleUnit.cs:82-88) — always exact.

(a) ROUND-TRIP EXACTNESS — exact except these enumerated cases:

The reconciler must force/require the booster off in the diorama (the dev build ships boosters).

### Risks

- THE AUTO-END BLOCK (battle.cs:180-207) is the one found hard blocker: without the new `!NetSyncDiorama.Active` gate, killing the final enemy inevitably runs victory/close sequences, writes ff9.btl_result and btl_flag (both OUTSIDE the snapshot bracket), fades the screen out permanently, and re-runs ManageBattleEnd (→ BattleAchievement.UpdateEndBattleAchievement) every subsequent frame. A reconciler-side dodge is racy-by-construction (die_seq 4→5→DelCharacter spans 2 frames vs the 150 ms tick).

- A die_atk (AttackOnDeath) enemy that is mid-'busy' state would defer die_seq arming (DeathStatusScript.cs:33, btlseq.cs:339) — in the diorama no commands run so busy should always be false, but if B3.x later mirrors host actions as local commands, a killed die_atk enemy could hang at die_seq 0 until the mirrored command clears.

## TRANCE — verdict: CORRECTED

### The verified answer

B3.4 TRANCE TOGGLE — ship glow + instant model swap (NOT glow-only, and NOT AlterStatus). Per unit on the guest main thread, edge-triggered:

```csharp
// wire.InTrance vs the local bit -- BattleStatus.Trance in BTL_DATA.stat.cur is THE flag
Boolean cur = btl_stat.CheckStatus(data, BattleStatus.Trance);
if (wire.InTrance != cur)
{
    if (wire.InTrance) data.stat.cur |= BattleStatus.Trance;   // RAW field write, never btl_stat.AlterStatus
    else               data.stat.cur &= ~BattleStatus.Trance;
    data.enable_trance_glow = wire.InTrance;                   // the ENEMY-side glow key; harmless parity for players
    if (data.bi.player != 0 && data.tranceGo != null && data.gameObject != null)
        btl_vfx.SetTranceModel(data, wire.InTrance);           // players ONLY (enemies have tranceGo == null -> NPE)
}
```
Do NOT write Data.trance (the gauge), bi.t_gauge, or stat.effects.

(a) BattleUnit.InTrance reads `(CurrentStatus & BattleStatus.Trance) != 0` and CurrentStatus is `Data.stat.cur` — the flag is one bit in BTL_DATA.stat.cur. (The gauge is the separate Byte Data.trance; HasTrance is bi.t_gauge.)

(b) TWO visuals with different drivers. (1) The pulsing glow is a pure per-frame render: btl_stat.SetStatusVfx iterates stat.cur, finds Trance's StatusGlowEffect (ColorKind 2, priority 10, from StatusData.csv row 23) and adds a btl_cnt-keyed 16-frame color pulse (TranceGlowingColor from BattleParameterList[serial]) via GeoSetABR("PSX/BattleMap_StatusEffect") + GeoAddColor2DrawPacket — for players gated on the Trance status bit && !Death, for enemies on Data.enable_trance_glow.
