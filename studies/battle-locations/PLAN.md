# Battle Locations — cross-referencing encounters to the map

> **Status: RESEARCH DONE, build not started.** Opened 2026-07-21 from a 4-agent parallel recon workflow
> over the kit source + the read-only Memoria engine clone (`C:\gd\FFIX\Memoria\Assembly-CSharp`). This is
> single-pass recon, not adversarially re-verified like the custom-summons/folklore-codex studies — treat
> file:line citations as agent-reported and spot-check before relying on them for a byte-level edit.

## 1. The question

`ff9mapkit/ff9mapkit/data/region_catalog.toml` already groups FF9's ~674 real fields into 73 logical,
story-visit-scoped zones (e.g. zone `evft` = Evil Forest = fields 152,250-262), derived from warp/field
ids. Can we build the same kind of map for **battles** — so a user can find "the Goblin fight in Evil
Forest" instead of needing to know a numeric battle-scene id?

## 2. Headline verdict

**Yes — but the obvious-looking shortcut is a trap, and the real path runs through data the kit already
half-built.**

FF9's battle scenes have their own id/name table, `ff9mapkit/ff9mapkit/_scenedb.py`
(`SCENES['BSC_<region>_<n>'] = encounter_id`, 856 scenes, regenerated from Memoria's open-source
`FF9BattleDB.SceneData.cs` by `_regen_scenedb.py`). Its region-code prefixes (`EF`, `IC`, `GZ`, `LB`…)
*look* like a ready-made zone map — but parsing them directly is the wrong axis:

- **~66% of the 856 scenes aren't tied to one place at all.** `BSC_B3_*` (176 scenes, 20.6%) isn't even
  real battle content — `ff9mapkit/ff9mapkit/battle/catalog.py:404-409`'s `_is_model_bucket` already
  excludes it as a model-preload holder (picking one as a field's encounter scene null-refs at
  `InitBattleScene` in-game). `BSC_WM_*` (274, 32.0%) is world-map/overworld, not field-scoped. `BSC_CAM_*`
  (100, 11.7%) is unidentified and its id range spans nearly the whole game — inconsistent with one place.
  Plus 14 dev/test-named scenes (`NOFUJII`, `TEST03`, `YASU00-05`, …).
- Even the clean-looking prefixes are **coarser than the field zone map**: `BSC_AC_*` (Alexandria Castle)
  spans both early- and late-game encounter ids with no story-visit split, where `region_catalog.toml`
  splits Alexandria Castle into 7 separate visit-arcs. Prefix-parsing alone gives an ambiguous, partial
  answer even in the best case.

**The reliable path is the same direction `region_catalog.toml` itself was built in: ask the FIELD, not
the scene.** A field's own `.eb` script says exactly which battle scene(s) it triggers, via
`SetRandomBattles` (random encounters) and `Battle`/`BattleEx` (scripted/boss fights) — and a *decoder*
for both already exists, tested at small scale, just never run as a full census. Looping it over every
real field and joining the result to `region_catalog.toml`'s existing zone/arc data produces the
scene→place map for free, with zero new parsing work. **Monster names ("Goblin") are a separate, currently
unbuilt piece — the raw16 struct has no name field at all — but the extraction mechanism is fully
understood from the engine's own open source and matches a pattern the kit already implements elsewhere
(per-language embedded `.mes` text pools, like item/ability names).**

## 3. The mechanism map

### 3.1 The existing field→zone map (for reference — nothing here needs to change)

`region_catalog.toml` (593 lines, 73 `[[arc]]` entries) groups fields by the FBG background-folder name
baked into `ff9mapkit/ff9mapkit/_fieldtable.py` (`FBG_TO_EVT`/`FIELD_BY_ID`, regenerated by
`_regen_fieldtable.py` from Memoria's open-source `EventEngineUtils.cs`
(`eventIDToFBGID`)/`FF9DBAll.Events.cs` (`EventDB`)). It's committed because it transcribes an
**open-source C# id↔name table**, not decoded game-asset bytes — the same provenance bucket as
`_scenedb.py` below.

### 3.2 The battle-scene table and why its names mislead

`ff9mapkit/ff9mapkit/_scenedb.py`: `SCENES['BSC_<region>_<n>'] = encounter_id`, 856 entries, regenerated
by `_regen_scenedb.py` from Memoria's open-source `FF9BattleDB.SceneData.cs`. Same provenance bucket as
`_fieldtable.py` (transcribed open-source labels, not extracted content) — safe to keep committed.

- `battle/catalog.py:430-438`'s `scene_name()` resolves an id back to its `BSC_` key —
  `tests/test_catalog.py:151` asserts `scene_name(67) == "BSC_EF_R007"`. **This resolves the "EF_R007"
  naming question from the earlier chat turn**: it is not a separate scheme, just the same `_scenedb.py`
  key with the `BSC_` prefix stripped (`battle/extract.py:342,350` — the donor param is "the part after
  `EVT_BATTLE_`", i.e. the Unity asset path `battlescene/evt_battle_ef_r007/`).
- `battle/catalog.py:412-418`'s `battle_scenes()` already excludes the `B3` model-preload bucket by
  default — reuse this filter rather than re-deriving it.
- No per-scene field-id back-reference exists anywhere (`battle/scene_data.py`, `battle/*.py` grepped for
  `field`/`fldMapNo`: zero hits). The only place the link *lives* is each field's own `.eb`, or at runtime
  in `battle/telemetry.py:113`'s live `fldMapNo` log — no static reverse index today.

### 3.3 The reliable path: field → scene, via a decoder that already exists

`ff9mapkit/ff9mapkit/eventscan.py` already has both halves, proven at per-field scale, never looped:

- `scan_encounter()` (lines 269-282) — pulls the 4 `SetRandomBattles` scene-id slots + the nearest
  `SetRandomBattleFrequency`; returns `None` if any operand is a **computed expression rather than an
  immediate constant** (`arg_is_expr` check) — it refuses to guess.
- `scan_battle_scenes()` (lines 285-305) — walks every entry for `Battle` (opcode `0x2A`, operand at
  `imm(1)`) and `BattleEx` (`0x8C`, `imm(2)`), masks with `BATTLE_SCENE_MASK = 0x7FFF` (bit 15 is a
  Steiner battle-state flag, not part of the scene id — cited to `EventEngine.DoEventCode.cs:962`), and
  likewise skips any expression-computed id.

Both are already wired in, but only per-field: `cli.py:1359` calls `scan_encounter` inside the
`import-chain` walker; `extract.py:507` calls `scan_battle_scenes` during a `--verbatim` fork (to carry
battle BGM). Neither is looped over every real field id to emit one table, and neither has dedicated test
coverage at batch scale (`grep -rln "battle_scenes\|scan_encounter" tests/*.py` → zero files).

**Operands are reliably immediate in practice.** A sample grep of the (separately archived, not in this
repo) `C:\gd\FFIX\reference\test2\` 817 real field-script text exports found 373 `SetRandomBattles(...)`
and 279 `Battle(...)` calls, **100% pure-integer operands** — e.g.:
```
SetRandomBattles( 1, 139, 343, 343, 343 )
Battle( 0, 336 )
BattleEx( 0, 7, 298 )
```
Each export also self-identifies its field id in a header comment (`#HW fileid 402 // Dali/Production
Area`), and `reference/field-manifest.tsv` gives the same id→place mapping as plain data — either works as
a cross-check, but the authoritative source for a real build is the `.eb`-based `eventscan.py` path (the
text exports are a derived/secondary artifact, not guaranteed complete or current).

**Conclusion: a full static census (`field id → {random scene ids, scripted scene ids}`) is practical
today.** The hard part — a decoder that correctly declines to guess at computed operands — is done. What's
missing is only the loop-and-join driver.

### 3.4 Monster names: unbuilt, but the mechanism is fully understood

No name field exists anywhere in the per-enemy data. `battle/scene_data.py:36-44` (`_MON_FIELDS`) and
`:50-95` (`_RESKIN_RANGES`, the cosmetic Bone/DieSfx/IconBone/ShadowBone fields) enumerate every decoded
byte of the 116-byte `SB2_MON_PARM` block; cross-checked against the engine's own struct definition,
`Memoria/Assembly-CSharp/Global/SB2/SB2_MON_PARM.cs:5-180` — 116 bytes, no `Name`/`MesId`/`TextId` field.
Confirmed by grep: zero hits anywhere in `ff9mapkit` for `MonsterName`/`MON_NAME`/`EnemyName`.

The actual mechanism, from the engine's own open source:

- `Memoria/Assembly-CSharp/Global/btl_init.cs:113-123` (`SetupBattleEnemy`): an enemy's display name is
  **string index `i` (0..TypCount-1) of a per-SCENE text pool**, assigned in the same order as the raw16's
  `SB2_MON_PARM` type list — `monsterList[i].name = FF9TextTool.BattleText(nameIndex++)`. That's the same
  `type_no` order `scene_data.py` already indexes for stats.
- Confirmed independently by the exporter, `Memoria/Assembly-CSharp/Memoria/Assets/Export/
  TranslationExporter.cs:135-144`: within a battle text pool, string index `< typCount` is tagged `#HW
  enemyname`, `< typCount+AtkCount` is `#HW attackname`.
- The pool is an embedded MES resource keyed by the **same numeric scene id `_scenedb.py` already has**:
  `Memoria/Assembly-CSharp/Memoria/Assets/Import/Text/BattleImporter.cs:38,81` —
  `EmbadedTextResources.GetCurrentPath("/Battle/" + index + ".mes")`. This sits in the identical
  embedded-MES-text family as item/ability/command names (`EmbadedTextResources.cs:9-28` lists sibling
  paths `itm_name.mes`, `sa_name.mes`, `com_name.mes`) — the same asset class `[[item_text]]`
  (`project-ff9-item-text.md`) already round-trips per-language, and the same cp1252-not-UTF8 lesson
  learned the hard way for `Data/Battle/*.csv` (`project-ff9-battle-tuning.md`) likely applies here too.

**One unconfirmed detail before building**: whether `Battle/<id>.mes` sits loose in the install's
`StreamingAssets` (like field `.mes` files) or packed inside `p0data*.bin` (needing a `UnityPy` read, like
field art/model assets). A five-minute probe of the user's own install settles it before any extractor
code is written.

**A false lead worth flagging so nobody rediscovers it the hard way**:
`Memoria/Assembly-CSharp/Global/Quad/Mist/QuadMistMonsterName.cs:6-119` is a hardcoded
`Dictionary<Int32,String>` (Goblin=0 … Airship=95) — but it's the **Tetra Master/Quad Mist minigame's card
list**, has no callers anywhere else in the source tree, and its index space is card order, not the
battle-scene `type_no` space. Not usable here.

No bundled community name table exists in this repo either (`reference/field-manifest.tsv` is the only
reference TSV present; `docs/BATTLE_DESIGN.md` uses "Goblin" only as a worked example, never a real table;
`docs/PROVENANCE.md` doesn't mention monster names at all yet).

### 3.5 Where this plugs into the kit today

- **`fork-report --explain` does not touch this at all.** `_cmd_fork_report` (`cli.py:4406-4421`,
  subparser `cli.py:6562-6568`) is scoped to NPC/dialogue/cutscene fidelity; an exhaustive grep of
  `forkreport.py` for `encounter|Battle|SetRandomBattles|0x2A` found zero hits — every "scene" match there
  is the camera `.bgs` scene or cutscene prose, not a battle scene.
- **InfoHub's `"scene"` kind is already taken — by battle scenes, not field cameras.** `infohub.py:30-31`
  (`KINDS`) includes `"scene"`; built at `:132-133` from `catalog.battle_scenes()` — i.e. the exact `BSC_*`
  catalog this study is about. Its `detail()` (`:555-557`) currently returns only `[("kind","battle
  scene"), ("id", ident)]` — **no location, no monster names**. Useful: `detail()` already supports a
  `usage_fn(id) -> [(field_id, name), ...]` hook (`:506-509, 580-584`), currently wired only for `model`
  entries — structurally identical to what a census-backed reverse lookup needs. **Naming implication: a
  new feature must not invent another `"scene"`-flavored catalog name — it should extend the existing one.**
- **The `battle-scene <donor>` inspector shows zero location today.** `_cmd_battle_scene`
  (`cli.py:3784-3829`, subparser `cli.py:6306-6309`) prints full per-enemy stats/AI/lint but the only
  "name" shown is the echoed donor argument (`cli.py:3797`) — no field id, no zone, no enemy display name.
- **Verb-naming precedent already exists for the overworld half of this problem.** `world-encounters`
  (`cli.py:6289-6304`) already does scene↔terrain/zone reverse-mapping — but scoped to the overworld
  `discmr.img` table only, never fields. The kit's general convention: bare plural nouns for browse
  catalogs (`scenes`, `items`, `models`, `catalog`), hyphenated `<domain>-<verb>` for inspectors
  (`battle-scene`, `find-rooms`, `world-encounters`).

## 4. Data model

```
field_id --[.eb: SetRandomBattles / Battle / BattleEx, via eventscan.py]--> scene_id (N per field)
field_id --[region_catalog.toml]--> zone token + arc name + story-visit
scene_id --[raw16 header TypCount + scene_data.parse_counts]--> per-type stats (already decoded)
scene_id --[Battle/<id>.mes, index 0..TypCount-1]--> per-type display name (NEW)

join: scene_id -> [(field_id, place_name, visit, encounter_type: random|scripted), ...]
      scene_id -> [(type_no, monster_name, stats), ...]
=> "Goblin (scene 67) — Evil Forest, fields 250-262, random encounter"
```

**Provenance constraint that shapes the whole design**: `_fieldtable.py`/`_scenedb.py` are committed
because they transcribe *open-source Memoria C# tables* — id↔name labels, no extracted game bytes. The
census (field↔scene links, from decoding real `.eb` bytecode) and the monster-name table (from an embedded
MES text pool) are both **decoded-from-the-user's-own-install content**, the same bucket as
`battlecsv.py`/`itemstats.py`'s existing "read-live" pattern and `extract-templates`. **Neither should be
committed as a baked table** — both must be generated on demand from the user's own install (cached
locally, gitignored, regenerate-on-stale), never shipped as repo data. This is the one place a naive
"just copy the `_fieldtable.py`/`_scenedb.py` pattern" instinct would be wrong.

## 5. The rung ladder (each rung = one offline-verifiable step; no game/deploy needed until rung 6+)

1. **Census loop** — run `scan_encounter` + `scan_battle_scenes` over every id in `_fieldtable.FIELD_BY_ID`
   (~674-818 real fields), emit `scene_id -> [(field_id, encounter_type)]`. Offline-verifiable against
   known cases already documented in `project-ff9-encounters.md` (scene 67 → field 250, Evil Forest;
   field 50 → scene 336, the Baku tutorial fight).
2. **Zone join** — resolve each census field id through `region_catalog.toml` to a zone/arc/place name.
   Offline-verifiable (pure data join, no game needed).
3. **Honest gaps, not guesses** — tag scenes with zero statically-resolved fields (pure `BSC_WM_*`
   overworld, `BSC_B3_*` excluded, computed-operand-only) as `unresolved`, never silently mislabel. Cross-
   check: the unresolved fraction should broadly track the ~66% non-placeable-prefix estimate from §2 as a
   sanity bound, not an exact match (different axis, coincidental overlap expected).
4. **Install probe** — confirm where `Battle/<id>.mes` actually lives in the user's install (loose file vs
   `p0data*.bin` via UnityPy). Five minutes, settles the one open unknown in §3.4 before writing code.
5. **Monster-name extractor** — per scene: read `TypCount` (`scene_data.parse_counts`, already exists),
   load `Battle/<id>.mes`, take entries `[0..TypCount-1]` in raw16 type order. Verify in-game-adjacent: the
   Goblin scene from prior in-game-proven work (`EF_R007`/scene 67) is a strong anchor test — if that
   doesn't come back "Goblin", the ordering assumption is wrong and needs revisiting before trusting the
   other 855.
6. **InfoHub wire-up** — feed the census + name data into the *existing* `usage_fn` hook for `kind="scene"`
   entries (`infohub.py:506-509,580-584`), so browsing a battle scene already shows "found in: Evil Forest
   (fields 250-262)" and real enemy names, no new catalog kind needed.
7. **New CLI verb** — a bare-plural browse command (candidate name: `encounters`, distinct from the already
   spoken-for `"scene"` InfoHub kind and from `world-encounters`' overworld scope) that answers "what
   battles are in zone X" / "where does monster Y appear", modeled on `world-encounters`' argparse wiring
   (`cli.py:6289-6304`).
8. **Polish (optional)** — enrich the `battle-scene <donor>` inspector (`cli.py:3784-3829`) with a
   "found in" section and real enemy names in its stat printout, instead of just the numeric `type_no`.

Rungs 1-3 alone (no monster names yet) are already a real usability win — "scene 67 → Evil Forest" beats a
bare id — and need zero new decoding work, only an orchestration loop. Rungs 4-5 are the piece that gets
you all the way to "Goblin."

## 6. Risks / caveats

- **A scene can legitimately belong to more than one place.** Shared/reused low-tier encounter tables
  (e.g. a generic "weak forest fight" reused across screens in different zones) mean the output is a
  *list* of places, not a single answer — don't force a 1:1 UI.
- **Computed-operand battles are invisible to static analysis by design**, not a bug — `eventscan.py`
  correctly declines to guess. Expect a small, bounded set of scripted fights that can't be place-tagged
  this way; document them as `unresolved`, don't silently drop or mis-tag them.
- **The `BSC_` prefix must never be treated as authoritative** — it's a useful sanity-check/fallback label
  (and the only signal for the ~1/3 of scenes a field-census can't reach, e.g. anything genuinely
  overworld-only), but §2/§3.2 already showed it's coarser than and sometimes orthogonal to the real
  field-based zone map.
- **Cost**: a full census touches ~674-818 fields' `.eb` bytecode plus (once built) 856 scenes' MES pools.
  Cache the result locally (gitignored) and regenerate on demand/staleness, matching the provenance
  constraint in §4 — don't recompute on every CLI invocation, and don't commit the output.
- **The `type_no` → name-index ordering assumption (§3.4) is read from engine source, not yet observed
  in-game** — rung 5's anchor test is load-bearing before trusting it broadly.
- **cp1252 encoding risk**: the project has already been bitten once by assuming UTF-8 on a Memoria text
  asset (`Data/Battle/*.csv` action names, `project-ff9-battle-tuning.md`) — read `Battle/<id>.mes` text
  with the same care/encoding-detection until proven otherwise.
