## 1. The .mes File As Instruction ROM

**Status:** KILLED (verify) · **Effort:** small · **Engine:** stock · **Round:** 1

**Pitch.** Move sequencing logic OUT of the 64KB .eb budget and INTO the text file, which has no budget. A dialogue entry with embedded signal tags becomes a program tape; the .eb shrinks to a tiny dispatch loop.

**Mechanism (as proposed).** In-text `[SIGL=n]` / `[INCS]` tags write `ETb.gMesSignal` when their glyph position appears on screen; script reads that back as `B_SYSVAR[8]`. Open a window with `WindowAsync (0x20)` whose text is *all spaces* plus a run of `[SIGL=k]` tags -- an invisible, zero-glyph window that emits a scripted sequence of integers over time as the typewriter advances. The .eb then holds ONE loop: `SET` pushes `B_SYSVAR[8]`, `SWITCH (0x0B)` dispatches, `Wait (0x22)` yields. N beats cost N bytes of .mes (free) instead of N unrolled bodies against `EB_FILE_BUDGET = 0xFFFF` (binutils.py:39). Text speed is the tempo dial; `SetDialogProgression (0xE3)` writes the same cell so the script can inject its own token into its own tape. Bank the tapes with `[TBLE=n]` so one .mes entry holds many programs selected by `SetTextVariable (0x66)`.

**Mechanism (screen correction).** Three fixes before it is worth a rung. (1) The budget arithmetic as pitched is wrong: a SWITCH tape still needs one case body per DISTINCT action in the .eb, so N beats only become free when they are the SAME parameterized beat replayed with different operands. Bank the OPERANDS, not the control flow — put the parameters in gScriptVector and index them with the already-shipped 0xD3 computed-index dividend, using the tape only as the ordered step clock. Relief then scales with data volume, which is the real win. (2) Never treat the typewriter as a clock. Text speed is a user setting, per-language line lengths differ, and TURBO-DIALOG (F9) collapses the typewriter entirely — the completion-journal PLAN already records turbo as the thing that eats windows mid-playtest. Use the tape strictly as an ORDERED sequencer with an explicit guarded wait_signal handshake per step (cutscene.wait_signal already mandates a timeout), and mark the entry `no_turbo`/`[NTUR]` so the tape cannot be fast-forwarded past a step the script has not consumed. (3) gMesSignal is ONE global cell shared with ordinary dialogue, and `[SIGL=n]` takes any Int32 with negatives meaning increment (content/text.py:292-293). A background tape running under live dialogue will clobber, or be clobbered by, any conductor/cutscene signal beat — so the design needs a declared reservation (e.g. tape values in a disjoint high band, and a lint refusing a tape concurrent with any signal-using say/open) rather than assuming exclusivity. Also unproven and worth benching first: an "invisible" all-spaces window still opens a real NGUI box — verify it can be hidden (`[NFOC]` plus off-screen `[MPOS]`) before building on it.

**Opcodes.** `0x20 WindowAsync`, `0x21 CloseWindow`, `0xE3 SetDialogProgression`, `0x66 SetTextVariable`, `0x0B SWITCH`, `0x22 Wait`, `B_SYSVAR[8]`

### Substrate verifier (engine expert) — REFUTED

REFUTED on substrate, though not on opcode existence. The opcodes check out: 0x20 WindowAsync, 0x21 CloseWindow, 0x22 Wait (`eb/opcodes.py:188,406,410`), 0x66 SetTextVariable (`:534`), 0xE3 SetDialogProgression → `ETb.gMesSignal` (`:445`), 0x0B SWITCH (`eb/cmdasm.py:26-27`, anchor delta 1), and `B_SYSVAR[8]` reads the signal back (`GetSysvar.cs:36`, and it is NOT in `exprsem.IMPURE_SYSVARS`, so polling it is pure). `[SIGL=n]` really does take any Int32 with negatives incrementing (`content/text.py:286-300`). None of that saves the idea.

(1) THE CHANNEL IS ONE INT WIDE AND HAS NO BACK-PRESSURE, so the "explicit wait_signal handshake per step" is only half a handshake. `gMesSignal` is a single cell, last-write-wins; the tags fire on typewriter position (`DialogBoxSymbols.cs:834-866`), and there is no script→typewriter lever except `CloseWindow` on a `[PAGE]`-split entry, which turns the page instead of closing (`Dialog.cs:616-624`) — and `[PAGE]` has **20 uses across all 64 stock blocks, in 2 blocks** (`studies/messages/SURVEY.md:345`), while `CloseWindow` itself can BLOCK on a voice clip (`DoEventCode.cs:527-558`). Without page-turn pacing the tape runs ahead of the script and values are dropped silently — a corrupt table, not a black screen, which is the worse failure class here.

(2) FIX (1) DOES NOT USE THE .MES AT ALL. Once the operands live in `gScriptVector`, the text file contributes zero bytes to the program — and `gScriptVector` is seeded by `B_LET` statements emitted **into the .eb** (`content/behavior.py:2444-2451`), RE-SEEDED at every Main_Init, i.e. field entry AND ~Reload (`behavior.py:1004-1010`). So the pitch's own corrected mechanism is the already-shipped 0xD3 table-ize lane from `studies/eb-budget/PLAN.md §4`, with a text file bolted on that carries nothing.

(3) THE BUDGET ARITHMETIC STILL DOES NOT CLOSE even if you stream seeds through `[SIGL=n]`. Measured: a seed statement `const(tid) const(i) B_VECTOR const(v) B_LET B_EXPR_END` is **15 bytes** (21 with const4), so the whole 0xFFFF offset budget (`binutils.py:39`) holds ~3-4k cells; the guarded `wait_signal` alone is **37 bytes** (`content/cutscene.py:265`) and a receive loop needs a store + index bump + bounds test per iteration. Relief therefore starts only in the 10²-10³ range, and at ~one queued signal per typewriter tick that is tens of seconds to minutes of tape — paid again on every field entry and every Reload. Meanwhile the measured budget pressure in this project is CODE, not operand volume: fort-condor's behavior bodies at 50-55KB, field 559's naive per-pair region test at 48KB (`studies/eb-budget/PLAN.md §1`), both fixed by structural compression and 0xD3 dispatch, not by data storage.

(4) FIX (3)'s RESERVATION IS UNENFORCEABLE EXACTLY WHERE THE KIT LIVES. A high-band convention cannot survive a ZERO write, and stock's entire idiom is `SetDialogProgression(0)` — field 41 contains 31 of them and **every one is 0** (`SURVEY.md §8b`). A `--verbatim` fork ships the donor's `.eb` and `.mes` untouched (only `Field()` is remapped), so a lint over kit-authored TOML cannot see the donor bytes that will zero the tape's position mid-run; the guard then times out and the script continues as if the step had happened.

(5) THE INVISIBLE TAPE IS DEAD BOTH WAYS, and this is the part that would have cost a playtest. A `[SIGL]` fires only when its text position APPEARS, driven by the label's render pass (the same `UILabel.OnFill` path that is the only thing re-asserting `[NTUR]`, `DialogBoxSymbols.cs:327-329`) — an off-screen or never-rendered window has no clock at all. A rendered-but-inhibited window is ARM B's exact precondition (`UIKeyTrigger.cs:984-988`): with every open window `FlagButtonInh` and a style in {128,16,144,160}, `B_KEYON` — which sets `scriptRequestedButtonPress` itself (`EBin.cs:1080`) — reads a Confirm nobody pressed, in the script's own input stream, on frame 1. So a background tape either has no clock, or is a visible plain box, or poisons every polled window in the field. `text.turbo_injectable` is the predicate; `SURVEY.md §7a-bis-2` records three existing lanes already unbenched inside it.

No DLL patch is smuggled in (everything named is stock/upstream Memoria), and the .mes really is a plain `_[TXID=n]…[ENDN]` text file with no u16 table of its own (`content/text.py:847`) — those two claims survive. The mechanism does not.

**Sharpened version.** Drop the ROM framing entirely and keep the one thing the census actually supports: `[SIGL]`/`[INCS]` is a text→script CLOCK, one Int32 wide, worth nothing as storage and a lot as timing. The defensible rung is the already-scoped `signal_at = "<substring>"` mid-line mark (`SURVEY.md` Tier-2 item 7B) — block a cutscene beat on a particular WORD (camera cut, SFX sting, flinch) instead of end-of-line only, on the proven guarded `wait_signal` shape with its 250-frame ceiling. It must ride a window the script opens and closes itself, at a style outside arm B's {128,16,144,160}, with `[NTUR]` on the entry, zeroing the cell before and after like field 41 does, and it must never be concurrent with any other signal-using window or a forked donor's own text. If someone still wants operand volume off the .eb budget, the honest rung is a bench that MEASURES the SIGL channel's loss rate under a page-turn handshake at three message speeds before anything is designed on it — and the prior is that CSV (the `TransportControls.csv` precedent) or 0xD3 structural compression wins on every axis that bench could report.

## 2. Field CALL/RET With A Save-Backed Stack

**Status:** SURVIVED · **Effort:** research-arc · **Engine:** stock · **Round:** 1

**Pitch.** Give fields a real calling convention: any field can invoke a reusable 'library field' (a generic shop room, a generic cutscene stage, a naming ceremony) and get control back where it left off -- with a genuine return-address stack living in the save file.

**Mechanism (as proposed).** `Field()` is `0x2B` and its operand is expression-flagged (`content/region.py:286` already emits `Field(<VAR>)`), so the destination is computed. The arrival entrance is `Global.Int16[2]` (`region.py:FIELD_ENTRANCE_IDX`). CALL = push `(caller_field_id, caller_entrance, arg0..)` onto a `gScriptVector` via the `0xD3` flexible_varfunc lvalue -- `B_VECTOR(vid, B_VECTOR_SIZE(vid))` with `B_LET` APPENDS -- then `set D8:2 = <callee entrance>` and `Field(<callee id>)`. RET = read the top frame with `flex(20,2)` indexed by `flex(21,1)-3`, write `D8:2`, `Field(<popped id>)`, then truncate by re-seeding size. Teardown is `ClearMemoriaVector (0x11A)`. The library field's `Main_Init` reads its arguments out of the same vector, so one physical field serves every caller.

**Mechanism (screen correction).** One mechanism detail is wrong: you cannot pop. `B_VECTOR_SIZE` (flex 21,1) is a PURE READ — `eb/exprsem.py:216-229` states every defined flexible_varfunc is a read, only the VECTOR/DICTIONARY lvalue trio is writable through `B_LET`, and the only shrink primitive is `ClearMemoriaVector (0x11A)`, which wipes the WHOLE vector id. So "truncate by re-seeding size" is not expressible. Fix: keep an explicit stack-pointer in its own cell — either a save-persistent GLOB Int16 in the ≥8712 band or slot 0 of the same vector — and let the vector's physical length stay at high-water. CALL = write the frame at `sp*FRAME` (append when `sp*FRAME == size`, overwrite in place when it is below), then `sp += 1`; RET = `sp -= 1`, read the frame at the new `sp*FRAME`, set D8:2, `Field(<popped id>)`. Never derive depth from `B_VECTOR_SIZE`. Two further framing notes: resume granularity is a field ENTRANCE, not an instruction — the caller's `Main_Init` must branch on D8:2 to a "returned-from-call" arm, so the reusable-library-field payoff is real but callers need one extra entrance each; and with the stack in the save, a mid-call save/quit must be survivable (either forbid saving inside a library field or make a nonzero `sp` at an unexpected field self-heal by unwinding one frame rather than black-screening).

(4) CLAUDE.md §8 — the nearest dead end is Path B ("a compiled dynamic Chase/Wander region test in `.eb`"), but that is the INVERSE problem: script-side point-in-polygon for arbitrary units, killed by 26-bit CalcStack overflow and a 20.8%-misclassifying AABB fallback. This idea hands the polygon test back to the ENGINE, which is the one oracle Path B established as sound. Adjacent, not covering. TWO honest dents, neither fatal: (a) the rung-0 fallback (N regions all armed, each body gated on a scratch "current step") is pure composition of shipped primitives — `region.flag_gate`, `gated_set_region`, and `camera.inject_camera_zones`' already-shipped "N regions, exactly one active via a shared flag" shape, driven by an already-shipped `[behavior]` clock/counter/schedule. Rung 0 therefore ships ZERO new engine capability, only a new authoring wrapper; the novelty lives entirely in the re-arm and in the product. (b) Regions fire on the PLAYER only (tags 2/3/10), so a searchlight can catch the player and nothing else — the idea is a hazard primitive, not a detection primitive, and "composes with idea 3 for the detection half" overstates what a region can see.

**Sharpened version.** A MOVING EXACT TRIGGER POLYGON — the region table read as animation frames. Sharpened by four findings in the source:

1. THE DISARM HALF IS ALREADY SHIPPED, SO THE BENCH IS NARROW. `build.py:6636` already fires `terminate_entry(255)` on a LIVE region at runtime (the one-shot lever, in-game proven), with a hard-won ordering law in its comment: terminate AFTER `EnableMove`, never inside the option body, or the player freezes. So half the cycle is proven. Bench ONLY the revival: arm region slot S, `TerminateEntry(255)` it from its own body, then `InitRegion(S, 0)` from a type-0 loop, and see whether it treads again. That is a ~20-line bench, not a feature.

2. THE REAL PRIZE IS THE argFlag EXPRESSION, NOT N FRAMES. `eb/disasm.py:11` — "opcodes >= 0x10 with operands carry a 1-byte argFlag bitmask; a set bit means that operand is an expression." `SetRegion` is 0x29, and `content/region.py:383` emits `29 00 <count> <points>` — that `0x00` IS the argFlag mask, currently always immediate. If a corner operand can be flagged as an expression, ONE region entry gets a VAR-DRIVEN quad: no N-entry budget, no frame quantization, arbitrary sweep length. TEST THIS BEFORE BUILDING N FRAMES. The likely landmine, and the thing to check first: `eventscan.py:478` records that real FF9 fields DO ship computed `SetRegion` args ("SetRegion is computed (expression args -> not statically placeable)") — so the engine supports it — but each point is a PACKED 32-bit `x = v & 0xFFFF, z = v >> 16`, and Path B's dead end pins the CalcStack at 26 bits. Composing `z << 16 | x` in-expression may overflow exactly where Path B died. Find a stock field with a computed SetRegion (scan for a non-zero argFlag on 0x29 across the 674) and READ WHAT IT DOES — that one disassembly decides between the cheap one-entry moving quad and the expensive N-frame build, before a line is written.

3. BUILD THE FLAG-GATED FALLBACK AS RUNG 0 REGARDLESS, BUT DO NOT CLAIM IT AS NEW. It is `camera.inject_camera_zones`' existing one-active-of-N shape with the selector driven by a behavior clock instead of by player position. Ship it as the safe floor, and pitch the arc's value strictly on (2) or on a proven re-arm.

4. THE LATCH AND THE GATE ARE ALREADY DOCUMENTED PROBLEMS — inherit the answers, don't rediscover them. `content/event.py:376` states the law in its own words: tag 2 is level-triggered, "edge-triggered 'once per visit' would need a leave-detecting re-arm zone" — a wall of fire WILL fire every frame without an explicit per-pass latch. And `MOVEMENT_GATE` means the hazard silently sleeps during a cutscene; for a sweeping hazard that is usually WRONG, so pass `movement_gate=False` deliberately and note it.

Scope it honestly: this is a PLAYER-hazard primitive (searchlight, advancing fire, closing walls), not a general detection primitive — regions see only the player. NPC-vs-volume stays with the behavior compiler's Chebyshev boxes.
