## 1. The Release Verb: charge and let go

**Status:** SURVIVED · **Effort:** small · **Engine:** stock · **Round:** 2

**Pitch.** FF9 has exactly one player verb (tap Confirm) because the kit only ever reads press-edges and held-state. `B_KEYOFF` — the release edge — is a pure, fully-decoded expression token that nothing in the repo has ever emitted. Reading it turns one button into three verbs: tap, hold, and release-at-the-right-moment.

**Mechanism (as proposed).** A seated code entry (InitCode) runs a tag-1 loop at `Wait(1)`. State in three GLOB bytes in the safe band. Arm: `const4(SQUARE) B_KEYON` sets `Global.Byte[S_CHARGE_ON]=1`. Accumulate, while armed: `const4(SQUARE) B_KEY` gates `Global.Int16[S_CHARGE] B_PRE_PLUS` — B_KEY is flagged (1, READ) pure in exprsem.py:147, so it is legal in a per-frame value, unlike B_KEYON which sets VoicePlayer.scriptRequestedButtonPress. Fire: `const4(SQUARE) B_KEYOFF` — also (1, READ) pure — jumps to a `SWITCHEX` (0x06) banding the accumulated value into weak/good/perfect/overcharged. Render the meter with the already-shipped `[[gauge]]` tile band (one SetTileAnimationFrame per tick) so no new art. Overcharge is the design payload: past the top band the switch falls into a fail case, which is what makes hold-to-release a *decision* instead of a delay. Outputs feed anything expression-shaped — `AddGi(<expr>)`, `SetHP(char,<expr>)`, a `Battle(<expr>)` scene pick, a `MoveTile` distance.

**Opcodes.** `B_KEYOFF`, `B_KEY`, `B_KEYON`, `0x22 Wait`, `0x06 SWITCHEX`, `0x07 InitCode`, `B_PRE_PLUS`, `B_LET`

### Substrate verifier (engine expert) — survives

SUBSTRATE SURVIVES; THE FRAMING DOES NOT. Every load-bearing opcode checks out. `_exprtable.py:36` maps 88=B_KEYOFF / 89=B_KEY, and `exprsem.py:147` classes both `(1, READ)` — "EBin.cs:1101-1114, pure ETb reads" — explicitly distinct from B_KEYON2/B_KEYOFF2/B_KEY2, which `dialogue-sync.md:100` pins as inert stubs ("handler only consumes the argument and returns 0"). So B_KEYOFF is the live handler, not the dead twin. I assembled it: `const4(32768) B_KEYOFF B_EXPR_END` -> `7e00800000587f`, `exprsem.analyze` = depth 1, writes=(), impure=(). SQUARE=32768 is real stock (qte.py BUTTONS, field 64's own prompts). InitCode 0x07 (opcodes.py:68), Wait 0x22 (:188), SWITCHEX 0x06 (cmdasm.py:26, disasm.py:22 "validated 100% boundary-aligned across all 5563 switches in the 676 shipping fields"). The always-on Wait(1) seated ticker is SHIPPED (gauge.py:289-334, type-0 entry + internal loop + init_code). Budget: tens of bytes, nowhere near the entry cap; the counter is nowhere near EXPR_VALUE_MAX=(1<<25)-1. No DLL patch is needed, and s44's `FilterScriptButtons` strips only Confirm|Special from B_KEYON/B_KEY, leaving B_KEYOFF explicitly unmasked (F1-BUILD.md:265).

FOUR MECHANISM ERRORS, all nameable and all fixable:
(1) THE GATE IS NOT A GATE. `exprsem.py` docstring: an operand token PUSHES eagerly; there is no short-circuit. `const4(SQUARE) B_KEY` cannot gate `Global.Int16[S] B_PRE_PLUS` in one expression — the increment fires every frame regardless. Needs `0x05 {key read}` + `JMP_IFNOT`.
(2) SWITCHEX BANDS NOTHING. `decode_switch` (disasm.py:117): 0x06 is explicit value/offset PAIRS — exact match, not ranges — and "a switch never has expression operands"; the selector is a preceding bare `0x05` statement (sc_probe.py:85-100). Banding needs `charge / width` computed first.
(3) WRONG TAG. The kit's ticker shape is a type-0 entry with ONE tag-0 function (`GAUGE_TAG = 0`, gauge.py:46/331), armed `init_code(slot, 0)`. Tag-1 is the WORLD dispatcher's loop tag (entrance.py), not a field code entry's.
(4) WRONG STATE HOME. `flags.py:53` FIRST_SAFE_FLAG=8712 is a BIT floor into the save-persistent campaign lane; per-frame transient scratch lives in the byte bands, which are nearly full — 2018-2031 qte (reserved), 2032-2039 netsync (ENGINE-WRITTEN EVERY FRAME under co-op), 2040-2041 choice mask, 2042-2046 numinput, behavior blackboard up to 1989.

THE ONE REAL HAZARD THE PITCH DOES NOT ADMIT: its Arm step uses B_KEYON, which `exprsem.py:146` classes IMPURE and puts in UNSAFE_TO_REPEAT because it SETS `VoicePlayer.scriptRequestedButtonPress` (EBin.cs:1080), cleared only once per event pass. `event.py:222-231` refuses turbo-injectable window styles at the polled_window call site — but that guard is LOCAL to one modal loop. - Per tick, three statements, each its own `0x05` + branch because RPN does not short-circuit:

B_KEYOFF'S ACTUAL ROLE, demoted honestly: a 4-byte saving over the prev/now derivation, nothing more — and it is worth ONE bench before it is worth any content. THE FALSIFIER, first and cheapest: on a scratch id, deploy two daemons side by side — one B_KEYOFF, one prev/now — each incrementing a visible gauge. If the B_KEYOFF gauge climbs continuously while the button is UP, the token is a LEVEL read, not a release edge, and it is deleted from the design with no loss; the prev/now daemon carries the verb either way. That is a 20-minute, one-playtest question, and it is the only question here that the files cannot answer.

### Substrate verifier (engine expert) — REFUTED

REFUTED at the engine source, on the piece the pitch names its own centerpiece.

**1. B_FRAME IS NOT A CLOCK — it is an animation-clip-length query.** Fetched `Assembly-CSharp/Global/Event/Engine/EventEngine.DoCalcOperationExt.cs:20-22`:
  `case B_FRAME: result = EventEngineUtils.GetCharAnimFrame(this.gCur.go, this.eBin.getv());`
and `f_EventEngineUtils.cs:1846-1853`:
  `GetCharAnimFrame(go, AnmNo)` -> looks up `FF9DBAll.AnimationDB.GetValue(AnmNo)`, returns `RoundToInt(clip.length * clip.frameRate) + 1`, or **-1 if the current object has no clip by that name**.
So B_FRAME(n) is a *static property of an animation asset* — how many frames long clip `n` is on `gCur`. It does not advance. It is not free-running. `B_FRAME Global.Int24[T0] B_MINUS const(window) B_LE` compares a constant against a stamp of the same constant: the window test is **always true**, every sequence has an infinite timing window, and the "dropped tick costs accuracy, not correctness" reasoning is describing a mechanism that does not exist. The parry window and the knock-rhythm lock — 2 of the 4 named products — are **entirely** this clock and die with it.

The pitch had the citation in hand and misread it: it says "exprsem cites DoCalcOperationExt.cs:21-26," and line 21 *is* the `GetCharAnimFrame` line. It also asserts "nobody in the repo has ever read" it — true, but the inference is backwards: nobody reads it because it is an anim-length helper, not because it is an undiscovered clock. Note the repo has already inherited this misread: `studies/field-coop/dialogue-census/spans.py:9` and `census.py:79` both file `0x6A`/B_FRAME under **TIMING**. That census label is wrong and should be corrected independently of this idea.

**2. The RPN is malformed, and the malformation is the project's worst known .eb failure.** `exprsem.py:162` gives `B_FRAME: (1, READ)` and the engine confirms it (`this.eBin.getv()`). The pitch writes it as a 0-arity push. `B_FRAME Global.Int24[T0] B_MINUS` therefore has B_FRAME consume `T0` as its anim-id argument, leaving one value where B_MINUS needs two — an **empty-CalcStack pop**, which this repo has already paid for: `studies/fort-condor/PLAN.md:79` ("pops an EMPTY CalcStack -> permanent per-frame desync, 8287 log errors, stuck") and `behavior-trees/PLAN.md:717`. It does not fail at build; it kills the event engine for the session.

**3. B_BAFRAME is not the fallback either.** Same file, line 17: `walkMesh.BGI_animGetFrame(getv(), ref result)` — the current frame of a **background** animation. It ticks, but it is per-field, it loops at its own clip length (so it wraps, breaking any subtraction), and a novel or BG-borrow field may have zero BGI anims at all.

**4. There is no sub-second clock in stock `.eb`, period.** Swept the whole sysvar surface (`GetSysvar.cs`, fetched): `7` = `gStepCount` (advances only while walking), `17` = `TimerUI.Time` (only live during a scripted countdown), `20` = `Settings.time` — **play time in SECONDS**, confirmed by the repo's own consumer, `studies/completion-journal/bench/README.md:304-305` (`B_SYSVAR[20] const(3600) B_DIV` for hours). 1 Hz. Useless for a chord, a double-tap, or a parry. Any real frame clock needs a new flex-varfunc or sysvar — i.e. **a DLL patch the pitch explicitly claims not to need** ("ENGINE: stock"). That is the undeclared dependency.

**5. Undeclared impurity in the sequence half.** `EBin.cs:1030-1033`: `B_KEYON` sets `VoicePlayer.scriptRequestedButtonPress = true` **unconditionally, before** the mask test. On a `Wait(1)` seated loop that synthesizes a Confirm into the dialogue/voice path every tick, forever — `exprsem.py` classes it IMPURE and puts it in `UNSAFE_TO_REPEAT` for exactly this, and `studies/completion-journal/PLAN.md:1268` states it outright. The pitch polls it per-tick and never mentions this.

**6. Undeclared storage allocation.** `Global.Byte[STEP]`, `Global.Int24[T0]` (3 bytes), and the mask table are gEventGlobal. Per CLAUDE.md §5 / `flags.py`, only byte 1089+ (flag 8712) is safe; 8512-8711 is stock read-mail payload, whole-byte-written by ordinary play. Unallocated globals here are a live save-corrupter.

**What survives, cleanly:** the CHORD. `EBin.cs:1050-1060` confirms the pitch's reading exactly — `B_KEY` is `(EvaluateValueExpression() & ETb.GetInputs(...)) != 0 ? 1 : 0`, a pure boolean OR-test over the mask. Two-thirds of the machine is real. The third that the pitch built the other two on top of is not.

**Sharpened version.** **"The seated loop IS the clock" — an `.eb` input lexer with no clock opcode at all.**

Drop B_FRAME and B_BAFRAME entirely; the pitch's rejection of counters was in service of a clock that does not exist, and the rejection is itself wrong. The argument was "counters drift when a tick is skipped." But the counter and the *input sampling* live in the same `Wait(1)` body: if `ProcessCode` skips the object, the tick is not counted AND the button is not sampled. They skip in lockstep. A free-running clock would not have rescued the missed sample — it would only have told you, precisely, how much input you lost. So the counter is not merely adequate, it is strictly the *correct* timebase for a sampled lexer, and it costs one `B_POST_PLUS` per tick.

Three pieces, all stock, all substrate-checked:

- **CHORD (unchanged, confirmed at `EBin.cs:1050-1060`):** `const4(L1) B_KEY const4(R1) B_KEY B_ANDAND`. Two pure mask-tests ANDed. Ship this one as-is.
- **EDGE, without the impurity:** do not poll `B_KEYON` on a per-frame loop — it asserts `VoicePlayer.scriptRequestedButtonPress` every tick into the dialogue/voice path. Instead keep a previous-state byte and compute the edge yourself: one `B_KEY` per button of interest per tick (N is small — 4-8), pack the bools into `Global.Byte[PREV]`, and `press = now & ~prev`. `B_KEY` is `(1, READ)`, genuinely pure, so a 60 Hz poll is free of side effects. This is a strict improvement over the pitch even ignoring the clock.
- **PHASE:** `Global.Byte[TICK]` bumped once per loop body, reset to 0 alongside `Global.Byte[STEP]` on any mismatching edge. Window test is `Global.Byte[TICK] const(window) B_LE` — a plain byte compare, nowhere near the 26-bit ceiling. The STEP-indexed expected-mask table stays as pitched (`flex(20,2)`, stock 0xD3, already in-game proven by `bttable_bench`).

Allocate STEP/TICK/PREV from `ff9mapkit/ff9mapkit/flags.py` at `FIRST_SAFE_FLAG` (8712) or above — never a bare `Global.Byte[n]` literal.

Surviving products: the **Konami-code easter egg** and **sequence-as-spell-id** (both only need ordering plus a generous window, which a tick counter gives exactly), and the **chord**, which needs no timing at all. The **parry window** and the **knock-rhythm door** are demoted from "stock `.eb`" to "needs a frame-accurate clock" — and the honest scope of that is a new flex-varfunc exposing a real frame counter, i.e. a small, well-shaped DLL patch on the `memoria-patches/` stack. Propose it as that, explicitly, rather than hiding it inside a misread opcode.

Bench order, cheapest-falsifiable first: (1) a two-button chord opening a door on a scratch field — pure `B_KEY`, no state, no timing, falsifies or confirms the whole input-read premise in one playtest; (2) the counter-phased double-tap; (3) the full 6-step sequence. Do not bench B_FRAME's "cadence" — the source already settles it.
