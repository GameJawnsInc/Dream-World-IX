### Substrate verifier (engine expert) — survives

The IDEA survives the substrate lens, but three of its named mechanism claims are factually wrong and one is already shipped.

WHAT HOLDS. Every token exists: B_OBJSPECA = 120 = 0x78 and B_SHIFT_RIGHT = 23 in eb/_exprtable.py; obj_var (content/region.py:237-242) documents the field codes 0=X, 1=world-Y-up, 2=Z, 3=angle, verified against field 706's vine climb. The 0b111 expression-armed 0xA1 is real (content/savepoint.py:376-378, exactly as cited). Byte budget is a non-issue: the loop body is O(children) bytes once, not per tick, and EB_FILE_BUDGET is 0xFFFF of table-relative OFFSET (binutils.py:38-48) — the pitch is right to say measure with eb_budget_used. The 26-bit CalcStack is not threatened either: field coordinates live in the 2-byte MoveInstantXZY domain, so sums and a >>2 stay four orders of magnitude inside ±2^25 (unlike Path B's cross products). No DLL patch is implied — every opcode named is stock; a forked field needs the fork-gate engine for reasons that predate this.

REFUTATION 1 — the architecture is impossible as named. 0xA1 MoveInstantXZY is OP_ARG_COUNT 3 / sizes [2,2,2] and 0x36 TurnInstant is 1 / [1]: NEITHER TAKES A UID. docs/OBJECT_CARRY.md:166 lists that family explicitly as "act on gCur/self, no uid operand". A single seated daemon emitting 0xA1 per child per tick does not move the children — it teleports the DAEMON object N times per frame and leaves it at the last child's pose. The uid-bearing forms are 0xAD MoveInstantXZYEx [1,2,2,2] and 0x87 TurnInstantEx [1,1] (the latter already encoded at eb/opcodes.py:130 with a test at tests/test_content.py:901). So the pitch is repairable, but "one-entry daemon + 0xA1/0x36" is not a mechanism that exists.

REFUTATION 2 — the primitive is already shipped, in exactly the per-object form the pitch rejected. content/platform.py:78-110 emits a tag-1 PERMANENT PER-FRAME LOOP whose body is MoveInstantXZY(obj(250).f[0], obj(250).f[1] + off, obj(250).f[2], arg_flags=0b111), gated on MAP.Bit[328+k], with SetPathing(0) and SetObjectFlags(7). That is the soft rig, with a vertical offset, on a live parent, in a field, on stock. The novelty left is generalization (arbitrary parent uid, lateral/orbit offsets, counter-rotation, damping), not the primitive.

REFUTATION 3 — the y sign is backwards. f[1] READS -pos.y and MoveInstantXZY arg2 WRITES a negated height (eb/opcodes.py:261-265; the pass-through therefore cancels, which is why savepoint works). For an inline read-modify-write, PLUS is DOWN — scene-ladder/rung1a_rig_proof.py:130-136 registers this as THE ARG2 Y-DOMAIN law after an in-game miss, and platform.py's own `+ off` is documented as "how far BELOW the player's feet". `obj(P).f[1] + dy_expr` for an up-offset child renders it underground.

REFUTATION 4 — an unadmitted requirement. SetObjectFlags(7) is collision exemption only (the CFLAG SEMANTICS LAW in content/prop.py:26-33); it does nothing about grounding. Any child with a vertical offset needs SetPathing(0) or the walkmesh re-grounds it — savepoint.py:968-972 records this as a live failure ("a walkmesh attach here snaps the moogle down INTO the container"), and platform.py's Init carries set_pathing(0) for the same reason.

REFUTATION 5 — 0xD4 is not a drop-in for AttachObject. AttachObjectOffset is count 3 / sizes [2,2,2] with NO uid (OBJECT_CARRY.md:167 flags precisely the mis-decode risk), so it names an offset, not a parent: it can only modify an attachment already made by 0x4C AttachObject(attached, carrying, bone). The kit has never emitted it, so its semantics are unverified — and its existence also undercuts the pitch's premise that stock offers no offset control.

REFUTATION 6 — the damper is numerically broken. B_SHIFT_RIGHT is an ARITHMETIC shift, so on a negative delta it rounds toward -inf: with (parent - child) = -1, (-1)>>2 = -1, and the child slides away 1 unit per frame FOREVER instead of converging, while a +1..+3 delta yields 0 and never closes. A one-token damper here is a one-token permanent drift. Use B_DIV (18, C-truncating toward zero, the division savepoint._trunc_div models) or a dead-band test.

Net: the substrate supports expression parenting — it is proven in shipped, in-game code — so the idea is not refuted. Its stated mechanism is.

Axis law, enforced at the emitter: dy is authored UP-positive and SUBTRACTED in the expression domain (f[1] reads -pos.y; arg2 negates again). Reuse platform.py's `off` convention and its wording so the two cannot drift apart.

Damping without a permanent drift: read the child's OWN transform (obj(255).f[i], the self form savepoint._self_angle_flip already uses) so a spring needs no scratch var at all — `self.x + (parent.x - self.x)/4` with B_DIV, never B_SHIFT_RIGHT, whose arithmetic shift makes a -1 delta creep forever and a +1..+3 delta never close. Add a lint rule: a shift on a signed difference in a per-frame integrator is a build error.

Static offsets: keep 0x4C AttachObject and add 0xD4 AttachObjectOffset AFTER it (0xD4 has no uid; it modifies the current attachment). Before shipping it, run tools/find_composite_props.py over the 817-field census to read a real field's 0x4C+0xD4 pairing and replicate it verbatim — it is currently never-emitted and its arg meaning is inferred, not proven.

Resource honesty: each child is a whole field object (entry, uid, model), and the rig needs its own reserved MAP-bit band with a per-field cap and a range check, mirroring platform_ride_bit's PLATFORM_MAX_PER_FIELD guard. Budget-check with eb_budget_used, and expect one frame of lag by construction (entry order vs actor update is not controllable) — which is why this sells as SOFT rig, orbit, counter-rotation and trailing motion, and why a rigid weld should still go through 0x4C/0x4C+0xD4.

First proof: the cheapest in-game discriminator is a two-child orbit on a walking NPC parent in a scratch slot — it falsifies lag, floor-snap and yaw-wrap in one playtest, and it is a strictly smaller change than the platform feature that already proved the primitive.

CALIBRATION IS DERIVED, NOT BENCHED. EBin.cs:1111-1122 is `ff9.rsin(getv() << 4)`; rsin's period is 4096, so B_SIN's user-facing period is 256 UNITS PER TURN — the same byte angle TurnInstant takes. Amplitude is ±4096. Therefore the kernel is exact, not tuned:
  x = cx + (B_SIN(t*s + i*k) * r) / 4096
  z = cz + (B_COS(t*s + i*k) * r) / 4096
`r` is world units directly. Envelope bound is r ≤ 8191 (r*4096 < 2^25) — a field is ~4000u wide, so no realistic orbit approaches the 26-bit wall. Field 64's `/360` is a ±11 SHADE wobble, a different application of the same constant, and it corroborates the 4096.

THE CLOCK IS MAP, NOT INSTANCE. `Instance` is VariableSource 2 = per-object; N props each running a tag-1 loop would each hold a counter that starts whenever its entry activates, and the crowd drifts. Instead: ONE daemon entry does `MAP.I16[t] = (MAP.I16[t] + 1) & 255` per tick (the mask is mandatory — unbounded it wraps negative at 32767 and feeds rsin a negative angle). N prop loops READ it. Per-actor offset `i*k` is a compile-time constant in each prop's own expression, so the wave is phase-locked by construction with zero per-actor state. This is the cross-entry scratch shape platform.py already ships (MAP.I16[3..6]).

SEAMLESS BY ARITHMETIC. A byte-masked counter times any `<<s` wraps exactly on the period (256·2^s ≡ 0 mod 256), so there is no seam to engineer. s=2 gives ~2.1s/revolution at 30fps; s=0 gives ~8.5s.

FREE DIVIDEND THE ORIGINAL MISSED: because B_SIN's unit IS the facing byte, the same counter drives orientation with no conversion — `TurnInstant(t*s + i*k + 64)` keeps an orbiting prop tangent to its own orbit, and a pendulum can bank. Two ops, one clock, no trig for the facing.

OPERAND 1 IS NEGATED HEIGHT AND OPERAND 2 IS WORLD Z — build the negation into the RPN. Getting this backwards puts the orbit's depth into the height slot, which reads as a prop sinking through the floor rather than as a wrong axis.
