## 1. The Continuity Ledger

**Status:** SURVIVED · **Effort:** medium · **Engine:** stock · **Round:** 1

**Pitch.** A save-persisted, append-only log of story beats in gScriptVector, so the game records not just WHAT happened but IN WHAT ORDER. Stock FF9 flags are amnesiac latches; this gives narrative state a history.

**Mechanism (as proposed).** One vector id (say 40) is the ledger. Every kit-authored story advance appends one packed Int26 record: push `Global.UInt16[0]` (SC) and the field id, combine as `sc*4096 + fieldid` (max ~12000*4096 = 49M -- OVER the 26-bit envelope, so pack as `(sc>>3)*4096 + fieldid` = ~6.1M, safely inside +-33,554,431), then write with the append idiom `B_VECTOR(40, B_VECTOR_SIZE(40)) <value> B_LET` -- index == size APPENDS, a missing id at index 0 CREATES. Emission is live today: `eb/exprasm.py:71-79` assembles both the `B_VECTOR` sugar and generic `flex(20,2)`. Reads are `flex(21,1)` for length and `flex(20,2)` at any computed index. Teardown for NG+ is `0x11A ClearMemoriaVector(40)`. Keep the `size<-0` seed idiom at field init so a stale save's ledger is inert rather than half-read. Consumers: order-sensitive dialogue branches ('you met the thief BEFORE the guard'), a recap, and the rewind substrate.

**Mechanism (screen correction).** The append idiom as written ("index == size APPENDS, a missing id at index 0 CREATES") is an unverified engine-semantics assumption — nothing in the kit relies on implicit growth. B_LET` cell writes). So emit append as three statements: read `n = <40> B_VECTOR_SIZE`, write `<40> B_VECTOR_SIZE (n+1) B_LET`, then `<40> n B_VECTOR <packed> B_LET` (n held in an entry local or a scratch cell so the size read happens before the grow). Creation is the same size write at n=0, done once behind a GLOB "ledger initialized" latch — NOT the per-field-entry `size<-0` seed, which would erase the history it exists to keep. Also give the ledger a fixed id well outside TABLE_ID_BASE (e.g. 900) and a hard cap on appends, since the vector rides the save and the budget/save size is unbounded otherwise.

## 2. Seed-Generation Migration Prelude

**Status:** SURVIVED · **Effort:** medium · **Engine:** stock · **Round:** 1

**Pitch.** A story-seed that can be REVISED after a player has already saved. Today `[startup] once = <flag>` is a one-bit latch: stamp once, never again. Replace it with a monotone generation counter so a later kit version applies only the bits it added, and never rewinds the player's own progress.

**Mechanism (as proposed).** Allocate one named GLOB word -- `Global.UInt16[g]` at a claimed byte in the safe band (the band is [8712, 16320) per `flags.py:53,69`, and a UInt16/Byte index is a RAW BYTE OFFSET, not a bit index, per `flags.py:17-21`, so the word must be carved out and registered like `AUTO_CUTSCENE_BASE` was). Main_Init emits a ladder of generation blocks: `0x05 SET(cond_cmp(GLOB_UINT16, g, 1, "<"))` then `0x02 JMP_IFNOT` over block 1; block 1 is the gen-1 bit writes ending in `set_var(GLOB_UINT16, g, 1)`; then the same shape for gen 2, 3... Each block is forward-only so JMP_IFNOT's unsigned read is legal (a backward JMP_IFNOT is a hard error at emit, `labelasm.py:203-204`). The generator side is a diff over two story-seed runs: emit only bits present in gen N and absent from gen N-1. `story-seed` already computes the demand set per field, so the diff is free.

**Mechanism (screen correction).** Two mechanism fixes. (1) Use GLOB_BYTE (0xD4) not GLOB_UINT16 (0xDC) for the generation counter: region.py:43-47 warns that a UInt16 write spans [idx, idx+1] and ZEROES the neighbouring byte, so a 0xDC counter silently clobbers whatever is allocated at idx+1 — a live save-corrupter in a band the kit packs densely. One byte gives 255 generations, far more than any mod will ship, and GLOB_BYTE touches exactly one cell. If a word is genuinely wanted, the allocator must reserve BOTH bytes as a BIT_REGION. (2) Register the counter as a reserved region in flags.py alongside AUTO_CUTSCENE_BASE (a named constant in the KIT-STANDING lane, >= KIT_STANDING_FLOOR = 14664, never in the campaign lane below it, whose windows are baked into a live save) rather than "a claimed byte in the safe band" — an unregistered claim is the exact aliasing failure the safe-band partition comment documents. The log therefore degenerates to an *ordering over a compile-time-fixed catalog*, not a general command log.
