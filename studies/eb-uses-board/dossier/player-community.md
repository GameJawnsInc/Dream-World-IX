## 1. The Seed Engine: a reproducible PRNG in RPN

**Status:** SURVIVED · **Effort:** research-arc · **Engine:** stock · **Round:** 1

**Pitch.** FF9's only randomness reachable from script today is B_SYSVAR[0] (Comn.random8), which is impure, shared, and unreproducible — so no randomizer, no seed code, no race parity. A Lehmer generator written in pure expression tokens gives a deterministic, save-persisted, seed-addressable random stream, and every opcode operand is already expression-capable, so chests, doors, encounters and shops become randomizable with no new opcode.

**Mechanism (as proposed).** State lives at `Global.Int24[b]` where `b = safe_bit>>3` (a Byte/Int16/Int24 index is a RAW BYTE OFFSET in the 2048-byte gEventGlobal, so bit 8712 == byte 1089). Step: `Global.Int24[b] Global.Int24[b] const(75) B_MULT const4(65537) B_REM B_LET B_EXPR_END` — I assembled this: 18 bytes, max_depth 3, one B_LET write, ZERO impure tokens, so unlike B_SYSVAR[0] it is legal inside a per-tick HUD/director value. 75 is a primitive root mod the prime 65537, so full period; peak intermediate is 75*65536 = 4,915,275, ~14% of the 26-bit envelope (±33,554,431) — no class-tag collision. const4 (B_CONST4) is required because const() is 2-byte and 65537 does not fit. Draw-in-range = `... const(N) B_REM`. Application is all argFlag, no new surface: chest reward `AddItem(<expr>,1)` (0x48, arg_flags=0b01); door `Field(<expr>)` (0x2B — the kit ALREADY has this as `content/region.py:field_to_var`); encounter `Battle(flags,<expr>)` (0x2A, arg_flags=0b10); shop `Menu(2,<expr>)` (0x75). Pools are `B_VECTOR` rows (flex(20,2)) so a Fisher-Yates shuffle runs in-script: swap vec[i] and vec[j] where j = seed%i, all indices computed. Seed entry rides the shipped `[[numeric_input]]` stepper; seed display via SetTextVariable(0x66)+`[VAR=]`. The arc's real deliverable is PARITY: the same 75/65537 generator in Python drives an offline `ff9mapkit seed verify` reachability pass over the gateway graph the kit already owns, so a seed is proven completable before it ships. Budget note: per randomized site ~20-40 bytes, so a 60-chest field is ~2 KB of the 0xFFFF offset budget.

**Mechanism (screen correction).** Two fixes. (1) The purity claim is wrong against the kit's own rule: `content/behavior.py:732` bars B_LET and every `B_*_LET*` from a HUD/per-tick value cell precisely because those assign through the expression — "zero impure tokens" is not the test, WRITE ops are banned too. So the step must be its own statement in a director/event body (one `_stmt(...)` per draw), never a `[[behavior.hud]]` value source or any re-evaluated-every-tick cell; a per-tick stepper would also re-roll the stream every frame and destroy reproducibility. (2) Guard the zero fixed point: 0 is absorbing for a Lehmer generator, and a fresh save's gEventGlobal is zeroed, so the seed install must clamp `seed = (seed % 65536) + 1` (numeric_input already bounds it) and the byte range 1089-1091 must be reserved in `flags.py` as a named 3-byte WordVar (the ferry origin at 1873 is the existing precedent) so auto-allocation cannot hand those bits to a story flag.

### Substrate verifier (engine expert) — REFUTED

REFUTED on four substrate grounds; two are hard, one is a hidden DLL dependency, one is a design error that voids the stated benefit.

1) THE STORAGE HOME IS OCCUPIED, AND BY BITS BAKED INTO A LIVE SAVE. `ff9mapkit/ff9mapkit/flags.py:51` — `FIRST_SAFE_FLAG = 8712` is defined as "start of byte 1089". Bytes 1089-1091 are therefore bits 8712-8735, i.e. the BASE of the CAMPAIGN LANE (`[FIRST_SAFE_FLAG, KIT_STANDING_FLOOR=14664)`), and flags.py's own partition note says: "The live opening campaign (372 members x 16 from 8712) spans 8712-14663 ... their windows are BAKED INTO A REAL SAVE: the floor must never move down, and the campaign lane must never be re-based while that playthrough lives." Reserving 1089-1091 aliases members 0 and 1 of a shipped campaign in an existing save — it is not an unallocated hole that "auto-allocation cannot hand out", it is already handed out. The cited 1873 precedent is the opposite shape: `FERRY_ORIGIN_X_INT24 = 1873` sits at the TOP of the kit-standing `kit_world_flags` band (14976-15007), and that band's `BIT_REGIONS` entry says it is "FULLY CONSUMED, live in real saves ... a new named world flag needs a NEW band, never these bits." So the proposal needs a newly minted reserved band, and the only clear space left is deliberately unreserved for modal results (bytes 1990-2005, `RESULT_WORD_CAP`) — a cost the pitch does not admit.

2) THE 26-BIT ENVELOPE IS THE LOAD-BEARING CONSTRAINT AND IS NEVER NAMED. `eb/opcodes.py:543-551`: every computed intermediate lands via `EBin.expr_Push_v0_Int24` (EBin.cs:1270-1274), which ORs the Int26 class tag into bits 26-28 with NO mask on `_v0`, read back as `(t0<<6)>>6`. Overflow therefore "does not truncate — the high bits collide with the VariableSource field and the entry is re-read as a DIFFERENT variable class" (echoed at `content/behavior.py:1018-1023`, which is why `ADJUST_MAG_MAX` is a hard fence). A Lehmer step `seed*A` must satisfy `A*max_seed <= 2^25-1`; with the pitch's own 16-bit state that caps A at 512, so 16807/48271 on 2^31-1 — and Schrage's trick's intermediates — are unrepresentable. The pitch names no modulus and no multiplier at all: the single parameter the substrate constrains is the one left blank. Worse, `B_REM` is C#-truncated, so one sign excursion (exactly what an overflow re-read hands you) yields negative remainders; guarding only the 0 fixed point does not close the domain.

3) "EVERY OPCODE OPERAND IS ALREADY EXPRESSION-CAPABLE" IS FALSE. gArgFlag is only consulted by the `getv1`/`getv2` readers; an operand read by raw `geti()` ignores it entirely — visible in `memoria-patches/s30-doeventcode-fork-walk.patch`, where REQ reads `scriptLevel = this.getv1()` but `tagNumber = this.geti()` in the same handler. Capability is per-OPERAND, per-opcode, and must be read out of DoEventCode each time. The kit's actually-proven expression-arg sites are a short list: 0x66 arg1 (`opcodes.py:580`), 0x7C arg0 (`:494`), 0xA1/0xCE/0xE7/0xF1 (platform/qte/gauge/savepoint), and computed `Field()` 0x2B (`docs/SCRIPTS_DLL.md:542`, the outpost warp). 0x48 AddItem, 0x2A Battle and 0x75 Menu — three of the pitch's five headline sites — are asserted with zero citation anywhere in the repo, and `docs/ATE_SYSTEM.md:126` shows the stock corpus gives no cover ("1040 call sites, ZERO expression-args").

4) ENCOUNTERS NEED A DLL PATCH THE PITCH DOES NOT ADMIT. Field/world encounter rolls are engine-side: `ProcessEncount` + the per-ZONE ENCRATE ladder drawing `Comn.random8` (`world/encounter.py:15,26,229`; CLAUDE.md's falsified-twice TOPOGRAPH entry). No `.eb` operand feeds that selection, so "encounters ... randomizable with no new opcode" is untrue on stock.

5) AND THE BENEFIT DOES NOT FOLLOW EVEN IF 1-4 WERE FIXED. A STREAM is consumption-order dependent; chest/door/shop consumption order is player-route dependent. Same seed, two players, two different worlds — which voids "randomizer, seed code, race parity", the entire justification.

WHAT SURVIVES (so the next round does not re-check it): B_MULT(17)/B_REM(19)/B_LET(44)/B_CONST4(126) all exist in `op_binary` (`eb/_exprtable.py:24-42`); `B_VECTOR` is real but is Memoria's 0xD3 `flexible_varfunc` sugar (fid 20, argc 2, `_exprtable.py:70`), on the stock baseline, and IS a valid B_LET lvalue (`behavior.py:1707-1711`); the purity critique in the MECHANISM is correctly read against `behavior.py:728-745` (WRITE_OPS/IMPURE_OPS are banned from a per-tick HUD cell, and B_SELECT + B_SYSVAR[0] both advance the shared RNG per `exprsem.py:121,183`); CalcStack depth is not a limit (`CalcStack.push` grows on demand); and the ~64KB entry budget is a non-issue — a Lehmer step is tens of bytes.

**Sharpened version.** THE SITE-HASH ENGINE (not a stream), scoped to operand sites with byte-level proof:

(a) PURE FUNCTION, NOT A STREAM. Each randomizable site computes `value = f(seed, site_id)` inline at its own consumption point — no shared cursor, so the result is independent of player route and actually delivers seed/race parity. (b) ARITHMETIC INSIDE THE INT26 ENVELOPE, STATED AS CONSTANTS. State `1 <= s <= 65536`; step `s' = (s * 243) % 65537` (243 = 3^5, a primitive root mod 65537, full period 65536; worst intermediate 243*65536 = 15.9M, comfortably under EXPR_VALUE_MAX = 33,554,431). (c) A NEWLY MINTED NAMED BAND, NOT 1089-1091 AND NOT 1873-1875. ## 2. Split ledger and PB delta

**Status:** SURVIVED · **Effort:** medium · **Engine:** stock · **Round:** 1

**Pitch.** A real speedrun timer with per-segment splits and a live +/- against your personal best, stored in the save, with no DLL and no external tooling. The run's clock is already in the engine; what is missing is the ledger.

**Mechanism (as proposed).** Clock: `B_SYSVAR[20]` is play time in SECONDS, engine-clamped to 8,388,607 and already used by the journal (`journal.py:1174`). For sub-second resolution, a seated director entry (the shipped behavior-ticker architecture: one entry looping `Wait(1)` at the ~20 fps logical tick) does `Global.Int24[b] B_POST_PLUS` each pass, giving a 50 ms monotonic counter that is save-backed. Split capture: a once-flag body per segment appends to a vector — writing at `index == size` APPENDS, so `const(V) const(V) B_VECTOR_SIZE <clock> B_LET` is the whole capture, 1 statement. PB comparison: vector 2 holds the PB run; delta = `B_VECTOR(1,i) B_VECTOR(2,i) B_MINUS` pushed into `SetTextVariable(0x66)` in EXPRESSION form (arg_flags=0b10 — the only way past the ±32767 immediate cap) and rendered by `[VAR=n]`. Sign is rendered without art via `[TBLE=bank]`: a 3-entry bank {AHEAD, BEHIND, EVEN} indexed by `delta const(0) B_LT` etc. Run reset = `ClearMemoriaVector(0x11A)` on vector 1; a finished run that beats PB copies 1 into 2 in a bounded loop (well under the measured ~200 vector iterations/tick). Splits survive save/load because gScriptVector is JSON-serialized into the save; the `size<-0` seed idiom keeps a stale save inert.

**Mechanism (screen correction).** Two corrections, neither fatal. (1) Vector-id allocation: the kit auto-allocates behavior data tables from `TABLE_ID_BASE = 1000` (`content/behavior.py:715`) and Main_Init SEEDS every registered table with a `size←0` wipe on every field entry (`content/behavior.py:2017`, `:2439`). A ledger vector that is registered as an ordinary kit table would therefore be wiped at every field load — the splits must live on an id OUTSIDE the kit's auto band and be explicitly excluded from the seed pass, with the `size<-0` seed applied only on an explicit run-reset. As pitched ("the `size<-0` seed idiom keeps a stale save inert") this is backwards and would erase the PB. (2) Sub-second resolution: the `Wait(1)` director counter only advances while that field's script is running, so it stalls across battles, menus, the world map and field transitions — it is a per-segment in-field stopwatch, not a run clock. Make `B_SYSVAR[20]` (global, monotonic, save-backed) the authoritative split clock and treat the tick counter as an optional in-field sub-second refinement, or the whole-run total will drift low by all time spent outside the field.

**Opcodes.** `B_SYSVAR[20]`, `B_VECTOR`, `B_VECTOR_SIZE`, `B_POST_PLUS`, `0x11A ClearMemoriaVector`, `0x66 SetTextVariable`, `0x22 Wait`

CLEAN (the idea's substrate claims check out):
1. **0x11F is genuinely free and contiguous.** `ff9mapkit/ff9mapkit/eb/_optables.py:543-571` ends the custom extended page at `0x11E: 'RemoveBattleStatus'`. `ff9mapkit/ff9mapkit/eb/_regen_optables.py:19-39` documents the 0xFF page (ops >= 0x112), asserts the static `opArgCount`/`opArgSize` tables end exactly at 0x112, and asserts `op == len(op_arg_count)` for each CUSTOM_EXTENDED entry — 0x11F slots in with zero gap. Encoding path exists: `opcodes.py:54` emits `bytes([0xFF, op & 0xFF])`, `disasm.py:244-245/323-324/383-384` decodes it as `0x100 | next`.
2. **Operands work, including expression operands.** Custom-page ops read every operand with `getv3()` (3-byte immediates, arg-flag-honoring); `ff9mapkit/ff9mapkit/tests/test_ext_opcodes.py:33-39` (`test_extended_expression_arg`) already pins an expression operand round-tripping through an extended op. So a split id / payload computed from `B_SYSVAR` is fine.
3. **No budget pressure, either kind.** A beacon is ~2 page bytes + 3 bytes/operand ≈ 8-14 bytes against the u16 entry-offset ceiling (`eb/ebsrc.py:708` `fpos > 0xFFFF`) — noise. And there is no CalcStack *depth* ceiling at all (`eb/exprsem.py:30-32`: `CalcStack.push` grows its backing `List<Int32>` on demand); only the 26-bit signed VALUE envelope (±33,554,431) binds, and split ids are small.
4. **Fix (1) is correct as stated.** `ff9mapkit/ff9mapkit/battle/telemetry.py:63-76` does hand-build JSON and write it with `new StreamWriter(path, true, UTF8Encoding) { AutoFlush = true }` inside `try { } catch { }`, anchored via `Path.GetDirectoryName(AssetManagerUtil.GetStreamingAssetsPath())`. The Newtonsoft law (`journalcatalog.py:398`, `s82-journal-menu-m1-story.patch:973`) really does ban the *library* (Unity-5.2 Mono `TypeLoadException` on JIT), not the shape. A second precedent exists: `s83-harness-agent.patch:413,2190-2196` already ships an append-only `events.jsonl` via `File.AppendAllText`. The write channel is doubly proven.

THE BREAK — fix (2) inverts the right answer:
**`Time.frameCount` is not a timebase in this engine, and the project has already registered that as a defect.** `memoria-patches/s46-folklore-render-rig.patch:939-942` is an explicit `REPAIR ... HIGH`: a window "previously converted to a FRAME count at an assumed 60fps ... only equals 60 real frames/second when vsync is off; Memoria defaults vsync ON (GraphicsSection.cs:35) and Unity vsync always overrides targetFrameRate (FPSManager.cs:41-45)". `studies/folklore-codex/RENDER-RIG.md:154-156`: "a 144Hz panel would close the window in 0.4× the clip; the window now counts `Time.deltaTime` seconds." The fix direction the codebase actually took was frame-count → wall-clock seconds. The pitch mandates the exact reverse, and calls it the hardening.

For a *split beacon* this is fatal, not cosmetic: `Time.frameCount` advances at the runner's display refresh, so the same real run yields splits 2.4× apart on a 144Hz vs a 60Hz panel. A leaderboard keyed on that is meaningless. The alternative logical ticks are no better — they are per-scene and not monotonic across the run (`world.OnUpdate20FPS` at ~20Hz for overworld, `FieldMap.HonoLateUpdate` at ~30Hz and documented as *dropping* events in `s21-dev-hotkeys-f6-f10.patch:11` and `s43:1138`), and `s33-fork-fldmapno-arg-lookups.patch:77` shows `FPSManager.DelayMainLoop` deliberately stretching the main loop on load. The existing global clock, `Settings.time` via `GetSysvar(20)`, is 1-second granularity and engine-clamped to 8,388,607 (`journal.py:1172-1174`) — fine as a cross-check, useless as a split.

TWO SECONDARY FINDINGS the pitch understates:
5. **Telemetry is the wrong side of the DLL line to copy wholesale.** Telemetry lives in the mod-shipped `Memoria.Scripts.<Mod>.dll` Overload channel — zero engine rebuild, kit-emitted at deploy (`telemetry.py:201-227`, `Scripts/Sources/Telemetry/`). A new `.eb` opcode lives in `EventEngine.DoEventCode.cs` — a `memoria-patches/` entry with a full `build_memoria.py` rebuild, bundle re-cut, `verify_fork_gates`, and the DANGEROUS auto-deploy-over-live-install caveat. The pitch declares `ENGINE: dwix` so it is not *silent*, but "one new extended opcode" reads far cheaper than it is. Users would need the `dwix-custom-memoria-*.zip` bundle to run a beaconed field — acceptable for forks (which already require it) but a hard gate on novel fields, which currently run on stock.
6. **The capability probe's stock-engine behavior is asserted, not established.** The pitch's guard assumes `GetSysvar(<unreserved code>)` on stock returns a benign 0. Nothing in this repo states the default-case return of `EventEngine.GetSysvar.cs:8-106`; `journal.py:1211` only notes that a code "has no case". And the probe cannot rescue the real hazard anyway: on stock Memoria a literal `FF 1F` has no `opArgCount`/`opArgSize` entry (static tables end at 0x112), so if the ad-hoc dispatch does not consume the operand bytes the instruction stream desyncs into garbage — the classic black-screen class. The beacon degrades catastrophically, not gracefully, off-engine. The reserved-index instinct is right (`B_SYSVAR` reads a single byte as the code — `content/region.py:73` — so 0-255, with 192 taken by the world-location path per `s33...patch:104`; plenty of room above 200), but it needs to be a hard gate, not a probe.

**Sharpened version.** **Split beacon for LiveSplit — corrected timebase, hard engine gate.**

`0x11F SplitBeacon(split_id, payload)` on the 0xFF page (verified free and contiguous after 0x11E), added to `CUSTOM_EXTENDED` in `_regen_optables.py` with shape `[3, 3]` so `getv3` arg-flags let either operand be a computed expression. Ships as a `memoria-patches/` entry touching `EventEngine.DoEventCode.cs` — stated up front as an engine rebuild + bundle re-cut, not a kit-only feature.

**Timebase, inverted from the pitch:** the beacon's primary field is `Time.realtimeSinceStartup` as a float (monotonic, refresh-rate-independent, already the codebase's idiom — `s33...patch:77` uses it for load-delay math), NOT `Time.frameCount`. `s46-folklore-render-rig.patch:939-942` is the registered precedent: this project already had to repair a frame-count window *to* wall-clock seconds because Memoria defaults VSync ON and Unity vsync overrides `targetFrameRate`, so `Time.frameCount` runs at the runner's panel refresh. Emit `Time.frameCount` too, but as a diagnostic column explicitly labeled refresh-dependent, never as the split value. Add `Settings.time` seconds (the engine's own play clock, `GetSysvar(20)`) as a third column so an auto-splitter can cross-check RTA against game-time and detect a paused/menu segment.

**Write channel, copied from telemetry exactly:** one JSON line per beacon, hand-built with string concat (Newtonsoft library banned, JSON shape is not — `telemetry.py:63-76` is the working precedent, `s83`'s `events.jsonl` the second), `new StreamWriter(path, append: true) { AutoFlush = true }`, path anchored via `Path.GetDirectoryName(AssetManagerUtil.GetStreamingAssetsPath())` so it lands beside StreamingAssets rather than inside a mod folder, whole call wrapped in `try { } catch { }` — a beacon must never break an event. Dormant by default behind an ini gate, the way `s83` arms off a file, since one game install is shared across worktrees.

**Engine gate instead of a capability probe:** do not rely on an unverified `GetSysvar` default. On stock Memoria a bare `FF 1F` has no entry in the static `opArgCount`/`opArgSize` tables (which end at 0x112) and risks an instruction-stream desync into a black screen, so the guard must be build-time, not runtime — `ff9mapkit lint` refuses a `.eb` carrying `SplitBeacon` unless the field's manifest declares the dwix engine requirement, the same way forked fields already declare the s23-s33 fork-gate dependency. Reserve the companion `GetSysvar` index deliberately above 200 (the byte-wide code space is 0-255; 192 is the world-location name path) and document the reservation in the same patch so a future sysvar addition cannot collide silently.

Budget is a non-issue and should be stated as such rather than hedged: ~8-14 bytes per beacon against the u16 entry ceiling, and no CalcStack depth limit exists at all — only the 26-bit signed value envelope, which small split ids never approach.

### Novelty verifier (project historian) — REFUTED

REFUTED on three independent grounds — the target application already ships, the mechanism exists twice in-project, and the one genuinely new element is governed by a law that makes it the wrong shape for the stated audience.

(1) THE LIVESPLIT AUTO-SPLITTER ALREADY EXISTS IN THIS ENGINE, AND THE PROJECT HAS ALREADY READ ITS SOURCE. Memoria ships `Memoria\Speedrun\AutoSplitterPipe.cs` — a named-pipe IPC to LiveSplit with a generic `SignalTrigger` entry point, `SignalBattleWin`/`SignalBattleEnd` on top of it, fenced by `Configuration.Speedrun.IsEnabled` (AutoSplitterPipe.cs:44-47, :80-81), fired from `btl_sys.cs:155` via `CheckForecastMenuOff`. This is not a discovery to be made — it is documented at file:line across studies/battle-coop/b34-recon.md (lines 43, 136, 146, 243, 284, 472, 530, 575, 580) and studies/battle-coop/diorama-lane.md (lines 95, 322, 386-387), where it was audited as risk R6 for co-op hygiene. The pitch's headline — "drive a real auto-splitter" — describes a pipe the player's engine already opens.

(2) THE PROJECT HAS TWO SHIPPED, PLAYTEST-PROVEN OUTBOUND GAME→EXTERNAL CHANNELS, and the pitch's MECHANISM section is a restatement of their constraints. (a) `memoria-patches/s83-harness-agent.patch` (★ playtest-proven 2026-08-27, now at protocol v5) publishes `ff9harness/state.json` every other frame and APPENDS `ff9harness/events.jsonl`, carrying field id, position, rendered dialogue, battle epoch/result/units, menu group — and critically `g.watch(*bits)`, which publishes arbitrary `gEventGlobal` bits in every later sample (ff9mapkit/docs/TEST_HARNESS.md:483-484). That already IS a script→outbound beacon: an `.eb` sets a flag, an external driver reads it at ~15 Hz with an absolute `Time.frameCount`, with zero new opcodes. It also already ships the PNG capture and per-run artifact ledger the pitch gestures at for OBS. (b) `ff9mapkit/ff9mapkit/battle/telemetry.py` writes `<game>/ff9mk_battle_telemetry.jsonl` via the Overload hub. The pitch itself concedes this, saying "the real constraints to copy from that module are: anchor beside StreamingAssets, try/catch every write, append+flush per line" — all three are already implemented in BOTH modules (telemetry.py's `Emit` uses `Path.GetDirectoryName(AssetManagerUtil.GetStreamingAssetsPath())`, `AutoFlush = true`, bare `catch { }`; s83 uses `WriteAtomic` with the sharing violation deliberately swallowed). Building a third file-based append-only outbound log with the same anchoring and the same failure discipline is an instance, not a capability.

(3) THE NEW OPCODE COLLIDES WITH AN ALREADY-TAKEN DECISION, AND THE AUDIENCE IS ON THE WRONG ENGINE. studies/eb-budget/PLAN.md §2 sets THE ESCALATION LAW: an unknown opcode falls through `EventEngine.DoEventCode()`'s `default: return 1` — a SILENT NO-OP, not a crash — so any extended-opcode path must be a declared `engine = "dwix"` field requirement, a build-time stamp, a deploy-time refusal, and a runtime capability probe. CLAUDE.md §5 makes stock-Memoria independence for novel fields a user-facing property; a beacon opcode revokes it for any field carrying one. And the stated beneficiaries — auto-splitter users, leaderboard submitters — run stock FF9 + stock Memoria, so an opcode beacon fires only for people who installed the DWIX bundle, i.e. nobody submitting an FF9 run.

FACT-CHECK OF THE NOVELTY CLAIM ITSELF: the narrow claim "zero `.eb`-facing surface added across the live patches" holds — I grepped every file in memoria-patches/ and found no added `DoEventCode` opcode case and no added `GetSysvar` case (s33's `GetSysvar(192)` at line 104 is a pre-existing managed READ of the world-location name label; s82's `ev.GetSysvar(c.A)` at line 384 is the Journal's C-record reader calling the existing API). But a true census fact does not establish that the capability is missing — it establishes only that the project routed around the opcode table, three times, deliberately.

ONE FACTUAL CORRECTION TO THE PITCH: "nail down the `<frame>` source (the engine's own frame/tick counter, not a wall clock)" is under-specified in the direction s83 already paid for. s83 design point (1) is that `Time.frameCount` is usable only because every schedule is an ABSOLUTE frame decided at least one frame ahead — Unity does not order component Updates, so a "now" stamp is sampled either side of the publisher. And s83 rev 2 E7 records that `timescale` decouples render frames from logical ticks entirely (at 0, `Block`/`IsHeld`/the ack keep advancing while the engine executes nothing). A render-frame count is therefore not run time, which is precisely what a splitter needs.

**Sharpened version.** The sharpest surviving version drops the opcode, drops the new file format, and keeps only the sliver no existing channel covers: an `.eb` author has no first-class way to say "emit the semantic event BOSS_DEAD here."

`[beacon]` — a kit-side TOML block that compiles to PURE STOCK `.eb`: each declared beacon is a write to a reserved `gEventGlobal` bit in the 8712+ safe band (`ff9mapkit/ff9mapkit/flags.py`), allocated and named at build time, emitted into a sidecar `beacons.toml` next to the deployed field. Zero engine surface, so it runs on stock Memoria, keeps `engine = "stock"`, and is immune to the ESCALATION LAW entirely. Consumption is then a routing choice the USER makes, and all three routes already exist:
  - DEV/CI: `g.watch(*bits)` in the s83 harness reads them as published state with an absolute frame stamp — no new code at all, just generated `watch` calls from the sidecar.
  - LIVESPLIT: a driver-side mapping from beacon name to `AutoSplitterPipe.SignalTrigger`, reusing Memoria's existing named pipe and its `Configuration.Speedrun.IsEnabled` fence rather than minting a competing IPC.
  - OBS: the same sidecar, read by an external poller.

If a genuine engine hook is ever justified, the correct one is NOT a new `DoEventCode` case writing JSONL — it is exposing the already-generic `AutoSplitterPipe.SignalTrigger` to one reserved flag band, which adds no wire format, no third log file, and inherits a fence that is already off by default on a shared install. And whatever ships must carry a run-time source that is NOT `Time.frameCount`: s83 rev 2 E7 proves render frames decouple from logical ticks under `timescale`, so the stamp has to be the engine's own play-time accumulator (`Settings.time`, already read by the Journal's `rec.*` records) with the frame count kept only as a diagnostic companion.
