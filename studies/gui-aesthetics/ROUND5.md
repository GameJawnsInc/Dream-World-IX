# The Type Menu — Round 4

## Lead: what the measurements did to your question

You asked to nudge the text up, especially the hints, without breaking accessibility. Three things came back that change the shape of the answer.

**1. The size bump is real, cheap, and mostly free — but it is the smaller half of the hint problem.** The hint tier is 11px, one pixel *below* the Windows default (Segoe UI 9pt resolves to exactly 12px — verified natively). Raising it to 12px is toolbar-neutral and costs nothing. But live, on the Import tab at a 1920 window, that same hint text renders **231–255 characters per line** (verified by driving the real app and reading `label.width()`). The readable band is 45–75. Bumping 11→12 turns a 246-character line into a 226-character line. The size is one of three compounding penalties — smallest face, quietest colour, longest line — and the measure is the one nobody has ever fixed. **The two fixes want to ship together.**

**2. Accessibility: my own ground truth was wrong, and correcting it is the most valuable finding of the pass.** The brief told the generators the app is "deaf to the Windows text-size slider," implying a WCAG 1.4.4 defect fixable by computing sizes from `QApplication.font()`. Two directions independently falsified that:

- Windows' Accessibility → Text size slider writes `HKCU\SOFTWARE\Microsoft\Accessibility\TextScaleFactor`. It does **not** touch `NONCLIENTMETRICS.lfMessageFont`, which is where Qt gets its font ([VERIFIED: set the key to 150, broadcast `WM_SETTINGCHANGE`, `lfMessageFont` stayed at −12 'Segoe UI'; registry restored]). `TextScaleFactor` appears in **zero** Qt DLLs — scanned 338 DLLs under PySide6, ascii + UTF-16; the only hit is `Qt6WebEngineCore.dll`, which is Chromium's own code. **Qt cannot see that slider. No Qt app on your desktop tracks it.**
- Meanwhile the app **already honours** Windows Display → Scale correctly: QSS px are *logical* px, and dpr multiplies them, so a 13px label renders 19.5 physical px at 150% ([VERIFIED: `QT_SCALE_FACTOR` 1/1.25/1.5/2 → dpr 1.00/1.25/1.50/2.00, logical size unchanged]).

So the app is not failing 1.4.4 through a fixable defect. It resizes fine. What it lacks is a **text-only lever**, and on Windows the only lever that can exist is an in-app one. That relocates the accessibility work from "track the OS" (impossible) to "ship a dial" (a real swing, ranked below).

**3. The 12px ceiling is a hard, measured wall.** `forms_qt.py:98` is `note.setFixedHeight(16)` on a hint label. At 11px a line is 14.61 (1.39 spare); at 12px it is 15.94 — **0.06px of spare**; at 13px it clips by 1.27 ([VERIFIED: native `QFontMetricsF` + real `sizeHint` under the real QSS]). Any hint bump must lift that pin in the same commit. It is one line and it is not optional.

## 3. DICTION — *one 11px tier is doing six jobs; split it by what the text is FOR*

**FIX**, and it contains a real bug.

**The problem.** `role="caption"` is 37 sites and has become the junk drawer for "secondary." Censused it carries: teaching paragraphs, form-field hints, **next-step directives** (3 "→ then deploy…" wayfinding lines), **warnings**, status reports, and chip/overline labels. It conflates demotion-by-importance with demotion-by-length and gets both backwards — the longest text gets the smallest face, and a warning gets filed at 11px grey because "small = quiet" was the only tool.

**The sharpest instance is a defect, not a taste call.** `forms_qt.py:265`: on a parse error the hint label's help text is **destroyed** (`h.setText(f"⚠  {e}")`), and it is only restored when the value parses ([VERIFIED: one label per field, no second label exists]). The teaching text vanishes at exactly the moment the user is failing to type a valid value.

**The proposal.** Split rule: **is it read, or is it glanced.** HINT (12px, muted, measured) for prose attached to a control. NOTICE (body size, state-coloured, keeps its ⚠) for anything that *reports* — an error is never smaller than the field it is about. TAG (stays 11px) for chip + overline only. Plus: give the error its own label so the help survives the error that needs it.

**Prior intent, already in the code:** `style.py:462-464` says *"Never demote a diagnostic to 11px grey — demote the EXPLANATION, never the answer."* NOTICE is that comment's code.

**Risk.** Promoting warnings to body size may read as shoutier than it is — that is an eye's call and may want a subset. Scope note: the "~27 ⚠ sites" figure is **[FALSE — corrected]**; 27 is the count of the ⚠ *character*, and ~10 of those are HTML log lines already living in REGISTER's log registers. The real migratable set is ~15 label sites.

**Contrast, measured.** Error text at 11px on the card ground **passes 4.5:1 in all 8 palettes** (4.54–5.28) — the error's defect is size and the destroyed help, not contrast ([VERIFIED: `theme.derive()` over all 8]). **But a latent gap exists:** `error_text` is not fenced against `surface_3` and lands **3.84–4.23 (sub-AA) in the 6 dark palettes** — zero pixels today, because nothing grounds state text there. If NOTICE gets a chip/badge ground, that becomes live in 6 palettes. That is the NINTH-GROUND LAW: extend `derive()`'s `_grounds` tuple *first*, or don't give NOTICE a chip.

## 5. CALIBRE — *a text-size control in Preferences, because on Windows it is the only lever that can exist*

**SWING.** Absorbs FOUNDRY, DIAL, and CADENCE's P3 — see "what died," below.

**The premise, corrected.** You cannot track the OS text slider (finding #2 up top). What you *can* do is ship the dial yourself. Two Qt facts shape it, and one kills the option my own brief favoured:

- **QSS `font-size` accepts only px and pt.** `em`, `ex` and `%` are **silently ignored** and degrade to the inherited size ([VERIFIED, two independent probes, both styles: 0.5em / 1.0em / 1.25em / 2.0em / 4em / 150% / 2ex **all** render 12px = the inherit baseline. 0.5em and 4em rendering identically is only possible if the declaration is discarded]). **So FACT 3's "qss_em TRACKS ×1.50" row was measuring `inherit` under another name** — its 15.94 is byte-identical to the inherit row's. A type *scale* cannot be built from em; every tier would collapse to one number.
- **A computed px sheet tracks exactly** ([VERIFIED: computed body 13px→renders 13; at a simulated 150% base, computed 20px→renders 20]), and the re-render seam already exists — `shell.py:565` `_apply_density` is literally `self.setStyleSheet(qss(self.pal, self._density))`.

**The proposal.** `prefs.text_scale()` / `set_text_scale()` modelled byte-for-byte on the shipped `density()` / `set_density()` pattern (which already has Preferences + Ctrl-K + gear-menu entry points to copy). `style.qss(pal, density, scale=1.0)` computes the type rungs. **P1 gate: at scale 1.0 the rendered sheet is byte-identical to today's** — assert it, and P1 provably changes nothing.

**Requires QUARTO P3 first, load-bearing.** `_SCALES` owns only 3 of the 8 sizes. Scale it alone and at 1.5× you get an *inverted* app: the hint reaches 16px while the body stays frozen at 13px — the hint rendering larger than the body it annotates. **[VERIFIED: 5 hard px literals in the template — `:102` 13px body, `:439` 26px name, `:471` 34px glyph, `:493` 15px h3, `:564` 11px badge.]** Plus **three sizes live outside the QSS entirely** (`hero.py:298/348` `setPixelSize(11)/(13)`, `hero.py:42` `_WORD_PX=40`) that no `qss()`-time multiplier can ever reach — see PLINTH.

**Risk.** This is the swing. **75** `setFixed*`/`setMinimum*`/`setMaximum*` sites in `workspace/*.py` ([VERIFIED by enumeration]), essentially all unaudited. Two are known: `forms_qt.py:98` clips at 1.25× ([VERIFIED]); the `?` concept badge's **box** overflows at **1.25×**, not 2.0× as its own direction claimed ([VERIFIED: `QToolButton.sizeHint` 20×24 vs the pinned `setFixedSize(22,22)` — one rung *earlier* than budgeted, and inside the proposed range. Its glyph *ink* survives to 2.0×, so an ink-based fence would pass vacuously]). The badge's `border-radius: 11px` is documented as geometrically half of that 22 — a circle; scale the font without the box and the `?` clips, scale the box without the radius and the circle becomes a rounded square. And the toolbar: at 150% the body is 18px, and 14px already costs an item at 1280. **[VERIFIED: the toolbar chevrons rather than clips — `test_workspace_a11y.py:141` already fences graceful overflow at 720px — so the cost is a *discoverability* cost, which `style.py:104` records as exactly how Ctrl-K and Preferences went invisible. Not a catastrophe; not nothing.]**

**Implementation traps worth the code comment:** `QApplication.font().pixelSize()` returns **−1** (the font carries pointSize=9, unresolved) — you must use `QFontInfo` ([VERIFIED]). And Python's `round()` is banker's rounding: `round(16.5) = 16`, and h3 at 1.1× is exactly 16.5. Pin the rule.

## 6. HEED — *read the slider Qt refuses to read*

**SWING.** Depends entirely on CALIBRE; worthless without it.

Qt won't read `TextScaleFactor`. **Python can, in six lines of `winreg`** ([VERIFIED: read/write/restore round-trip done]). Seed CALIBRE's default from it, so a user who has already told Windows they want 150% text gets it on first launch with no preference to discover, and the in-app control remains the override.

**Precedent the direction didn't cite, and it's strong:** `editor/theme.py:311` already ships `detect_os_dark()` — an HKCU registry read with a bare `except → default`, fenced by `test_editor_theme.py:226`. This is a sibling of shipped, fenced code, not a new pattern.

**Risks.** (a) **Taste, and it's the real one:** an app that scales when *nothing else on the desktop does* may read as broken rather than considerate. P3 (a Preferences line saying "following Windows text size: 150%") is the feature's alibi and must not be cut. (b) **Compounding is a correctness risk:** `TextScaleFactor` and Display→Scale are independent multipliers. Range **[VERIFIED: Microsoft Learn documents `TextScaleFactor` as [1, 2.25] = 100%–225%]**, so 150% DPI × 225% text = **337% effective**. It must clamp against 2.25 as the true top. (c) The px fences in `test_workspace_style.py` (`:73/:453/:454`) hard-pin rendered px — a registry-seeded default makes those tests **pass or fail depending on the developer's own accessibility slider**. The scale must be an explicit parameter defaulting to 100%, injected only by the app at startup.

## 8. GAUGE — *a measure that is a number is a measure for one font size*

**FIX / plumbing.** Only earns its keep if CALIBRE lands.

`widgets.py:203` already documents, correctly and at length, that *"a px cap is NOT a measure — it is a measure only for ONE font size"* — and then defines two px constants. Same defect, one level up.

**It is already out of band at rest:** the Build & Deploy crown note renders in a 420px Prose at **77.5ch** ([VERIFIED live]). The fence passes anyway because it hard-codes `WORST_13PX = 5.72` while that actual string runs **5.420** px/char. A constant divided by a constant cannot see a live defect, and it didn't.

**And it decays under any scale:** 420px is 62.9ch at 16px, 50.3ch at 20px, **38.7ch at 26px** — below the 45 floor. The measure would fail a low-vision user at exactly the setting they turned on to be helped, and no fence would notice.

**Proposal:** `widgets.measure(chars, font)`, `Prose(text, chars=68)`, recompute on `FontChange`.

**The one unchecked assumption, now checked, and it's a [FALSE] verdict against the proposal's convenient path:** `averageCharWidth()` is perfectly linear in size (so it's a sound *scaling* proxy — the direction's stated fear was wrong) but at 13px it reads **5.953**, above the entire real-prose band (5.420–5.890). `measure(68)` via averageCharWidth = **404.8px**, not 420 — it misses P1's own "zero pixels move at 100%" gate by 15px and re-wraps every Prose. A calibrated sample rate is required. **And be honest about what falls out:** to land exactly 420 at 68ch the rate would have to be 6.176 px/char, above every real string measured. **420 is not 68ch of this app's prose by any honest rate — it is 71–77ch.** Either the alias is `measure(71)`, or pixels move and you say so.

## 9. LEADING — *Qt CAN control line spacing — just not from the stylesheet*

**SWING**, gated, and the direction most likely to be net-negative — it says so itself, and it's right.

"No line-height in QSS" is true ([VERIFIED — I checked what the direction didn't: a widget stylesheet's `line-height: 200%` and `line-height: 200px` are both **ignored**, no effect, no warning]). But a QLabel set to RichText **does** honour CSS line-height: the same 11px string at width 420 is **30px plain and 45px at `line-height:150%`** ([VERIFIED]). The lever exists and has never been picked up.

**The trap under the trap:** Qt's percentage is proportional to the **natural line box**, not the font size. `line-height:150%` — the number a web author reaches for by reflex — renders **2.045×** the font size at 11px. And it isn't even a constant: it's 2.077× at 13px, because the box it multiplies is size-dependent. There is no single percentage that means "1.5" ([VERIFIED: you'd need 110% at 11px, 108.33% at 13px, 112.5% at 12px]). **So a `leading=1.5` API is a lie; take a raw percentage or resolve it from the polished font.**

**A second trap under that one:** the app's *real rendered* leading is 15.00px at 11px and 18.00px at 13px, not the `QFontMetrics` lineSpacing of 14.61/17.27 — Qt rounds up per label (`ceil`, exactly, at all six sizes tested). **Anyone reasoning from 14.61 is reasoning about a number that never reaches a pixel.**

**The footgun, and it is severe and silent.** `'ids < 4003 are real'` renders as **`'ids '`**. `&` survives; `<` destroys the remainder of the string with no error ([VERIFIED via `QTextDocument` round-trip]). In an app whose entire subject is field ids and comparisons, that is not hypothetical. `html.escape()` fixes it — **but the containment argument is false: the app already ships rich text outside Prose** (`shell.py:1546`, `shell.py:939`, `forms_qt.py:460/465`, `shell.py:2880`). Escaping in Prose contains Prose, not the hazard.

**Gate it.** On today's single-line captions there is nothing to lead. Sequence after COLUMN, A/B it, and if you can't see it, take the escaping fence as free hygiene and walk away. Good news: Prose's `heightForWidth` **stays honest** under rich text ([VERIFIED: cap holds, no clip regression]).

**Bonus receipt, on the baseline-grid question: the answer is no.** Segoe's natural line box lands on the 4px grid at exactly two sizes in range (12→16, 15→20); 13→18 misses. And 1.5× leading lands on the grid at exactly one size: 16→24. **The grid and 1.5 leading are mutually exclusive unless the body goes to 16px.** A true baseline grid isn't expressible at all — card heights are content-derived (the live Build & Deploy card measures **237px**, off-grid, and always will be, since its height is the sum of its children's hints).

## 10. GLOSS — *three registers: sans for what you operate, mono for what you copy, serif for what you read*

**SWING.**

The app already won this argument once, in the other direction. `style.py:474-481`, THE MONO REGISTER: *"Set in the body face they read as prose and the eye slides off them; set in mono they read as things you copy."* **The inverse is unspent** — the app's *explanations* are set in the UI face, so they read as chrome and the eye slides off them too. A gloss is a manuscript's marginal explanation, which is exactly what this text is.

**The genuinely useful discovery here is a Qt trap, and it's good.** Sitka Small, Sitka Text, Georgia and Constantia **all lack the → glyph**; Cambria has it ([VERIFIED: `QRawFont.glyphIndexesForString('→')` returns 0 for the four, non-zero for Cambria and Segoe]). **And `QFontMetrics.inFont()` lies about it** — it returns True for all five, because it consults the fallback chain. It is a broken per-face coverage test, the same class of trap as `exactMatch()`.
