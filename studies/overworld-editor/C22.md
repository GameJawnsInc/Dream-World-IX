# C22: the ledger stays true -- the files put back behind it

**Status:** FIXED, 2026-10-24. The open finding from C19: three `Donor.txt` sidecars in column 23 (rows 6-8) whose
last ledger rows did not name their bytes.

## What it was

The whole live folder had **19 such files**, all in blocks (21-23, 6-8): the sidecars, three Terrain meshes and one
Object mesh, on both discs. Each carried a last row from a 2026-10-06 `world-mountain` run (near (1452, -468), donor
5-6,15-16). Its `Donor.txt` row names `5,15`, but each file holds `0,0`, and so does every one of the 15 backups the
runs parked before writing, back to 2026-08-28. The files keep the original deploy's exact modification time.

The cause is in the west-seam continent's comp20 bench (`COMP20-BENCH.md`, "DEPLOYED LIVE (2026-10-06)"): its live
deploy began with "THE R4 REVERT live: restored 560 files from `r4-pre`". That restore was a plain file copy, which
keeps modification times and writes no ledger row. The R4 carve had been ledgered just before it, so wherever R4's
bytes differed from the restored ones, the last row still named R4's.

**Every one of the 19 holds bytes an earlier row of its own names** (mostly the 2026-08-28 `world-island`
deploy). They were restored to a state the ledger once recorded; none are foreign bytes.

## Why it mattered, and why nothing caught it

The editor trusts each file's LAST row:
- Promote and Revert carry a file under that row's writer (`draft._ledger_tags`), so these 19 would have gone into
  the game labelled as R4's `world-mountain` bytes;
- `river.deploy_ownership` reads a last-row mismatch as foreign.

The kit's own check, `world-ledger --drift`, could not see it, for two reasons:
- it hashed only `.ff9mesh` files, never the sidecars;
- it asked whether ANY row anywhere in the ledger named the bytes. All 19 pass that.

## What changed

- **`mesh.ledger_audit(mod_root)`** judges every deployed world file, meshes and `Donor.txt` alike, by the rows of
  its own (disc, cell, part):
  - `true`: the last row names its bytes;
  - `stale`: an earlier row names them;
  - `foreign`: rows exist and none names them;
  - `unledgered`: it has no rows.
- **`mesh.ledger_repair`** re-ledgers only the stale files. Each new row names the bytes now and carries the earlier
  row's own `argv` and `pipeline`, so the bytes stay attributed to the run that wrote them. A `repair` field records
  who repaired it, the row it was restored to, and the row it supersedes. Foreign and unledgered files are never
  touched, and the ledger is parked first.
- **`world-ledger --drift`** reports the three kinds; **`--repair`** runs the repair.
- **The overworld skill** says never to put world files back by hand copy, and what to run after one.

Tests (`test_world_ledger.py`): the comp20 restore in small (a deploy, a second ledgered deploy over it, then a
plain copy back) reads stale, and the old any-row rule passes it. Foreign, unledgered and parked copies are each
named. The repair re-ledgers only the stale files, under their own writer, and Promote's tag follows. A second
repair writes nothing, and the CLI round-trips. Two mutations each turned the tests red: the old any-row rule (3
failed), and attributing the repair to the superseded row (1 failed).

## On the live folder

- **Before:** `world-ledger --mod-folder FF9CustomMap-world --drift`: 19 stale, 0 foreign, 1,345 unledgered, out of
  2,518 files.
- **The repair:** the ledger was first backed up to `backups/FF9CustomMap-world.ff9world.jsonl.<ts>` in the main
  repo, and parked beside itself. `--repair` appended 19 rows (5,902 to 5,921 lines).
- **After:** 0 stale, 0 foreign. In blocks (21-23, 6-8), all 90 files have a last row that names their bytes (C19's
  own rule), and the sidecars now read `world-island`. Three Terrain meshes read no writer, because the row they were
  restored to never recorded one, and the repair does not invent one.

## Not here

- **The 1,345 unledgered files**, which are pre-ledger deploys. No row says whose they are, so the ledger cannot
  claim them. Each one is ledgered the next time a verb writes it.
