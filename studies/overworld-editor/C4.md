# C4: promote a draft, and the game follows (no DLL)

**Status:** built and in-game proven 2026-10-23 (`c4_lab.py run`, every registered prediction held on the second
run; the first run was invalid and is kept). Owner request: "Merge C1 to master, then start C4: promote a draft into
the live folder and have the game follow."

## What it does

On the forest card's draft row, after an Accept:

- **Promote** writes the draft's edits into the live mod folder, after a confirm. It runs `world-promote <draft>`, the
  CLI again.
  - Refused before any write when a file the draft edited changed in the live folder since the draft was made
    (another session deployed there).
  - Every write is backed up (`.bak-<stamp>`) and ledgered, like the deploy seam's, so later deploys read the bytes
    as kit-written.
  - The disc-4 mirror then runs in the live folder, which a draft cannot do (C1).
  - Every live file at the edited blocks, both discs and every part, is snapshotted first, in
    `<draft>/promotes/<stamp>/`.
  - The draft is then rebased: it equals the live folder, with no edits and nothing stale.
- **Revert promote** (`world-promote --revert <draft>`) puts every file at those blocks back to the snapshot, byte for
  byte, and removes the files the promote created. It refuses when one of them changed after the promote. The edit
  stays in the draft, so it can be promoted again.
- **Show in game** (dev checkout, `tools/world_reload.py X Z`) makes the RUNNING game re-read the world. The engine
  reads every block override when the world loads, so the reload is the route the terrain labs used since round 16:
  from the world map into bench field 6603, out of its door, the world loads fresh from disk, and then the engine's
  teleport puts the party at the accepted forest. It keeps the story's ScenarioCounter as it was, and it is on foot
  only.

## The first run was invalid, and said so

The lab ran `python -m ff9mapkit world-promote` from the REPO ROOT, where `-m ff9mapkit` finds the distribution folder,
not the package ("No module named ff9mapkit.__main__"). The promote never ran, and the game stood on grass after the
reload: P2 failed. P1 and P5 passed vacuously: P1 because no promote had happened, P5 on the old blocks' loads. Now:
the lab runs the CLI from the kit folder, as the World tab's job does (`worldforest.kit_cwd`), and P1-P5 are judged
only when both the promote and the revert ran. P5 also requires one load line per edited block.

## Tests

- `test_world_forestedit.py`:
  - promote writes the edits, mirrors in the live folder, backs up, ledgers and rebases;
  - revert is byte-exact and leaves the edit in the draft;
  - promote refuses over another deploy and writes nothing;
  - revert refuses over a later write;
  - an empty draft and a source outside the install both refuse;
  - the CLI's dry run, report, revert, and second revert (refused).
  - The disc-4 mirror is faked there (it needs the install's bundles) by a writer that copies to disc 4 and adds a
    Sea4, so revert is judged on a file the promote created.
- `test_worldforest.py`: Promote asks, then writes the live folder (the job runs `cli.main` in-process), the view
  returns to the game's stack, Revert appears, Show in game goes to the accepted forest, and Revert asks and restores;
  a refused promote says why and writes nothing; without the dev reload, Show in game never shows.
- **Found by the tests on the way:** the promote record hashed its "before" paths after it had overwritten them, so
  revert refused its own snapshot as damaged. The hashes are now taken from the snapshot bytes as they are copied.
