## What it does

"Sink an island" sits beside Add forest and Add mountain. Its card is the carry cards' frame with a sink's parts:

- **The islands are the cached island list** (`world.sinkedit.candidates`): `transplant.sink_candidates`, every real
  island of the disc with its verdict, now with its **outline** (`_plan_hull`, the convex hull of its land). It reads
  every stock block, 3 min 13 s on disc 1, so it is cached per install and disc in the kit's cache: stock land does
  not move under a draft (the sink reads stock).
- **A click picks the island under it** (the smallest outline holding the point, else one within 6u), and the
  command uses the island's own point (the one `world-sink --list` prints), not the click.
- **The ghost is its outline at sea level**, filled: where the sea closes.
- **The preview is the island's precomputed verdict**: a whole-tile sink, its land only with its neighbours kept, or
  the cluster its water joins ("With its cluster"); an island with an entrance needs "Allow entrances".
- **Check** runs `world-sink --dry-run --report-json` (new: the verdict as data, the failing gates' blocks as
  marks). **Accept** runs `world-sink` into the draft twice: disc 1, then the same sink on disc 4 with
  `--skip-mirror`.
- Each Accept is a `[[sink]]` recipe row. Show in game is not offered for a sink: the island's point is open sea.

## THE DRAFT'S DISC-4 HALF

`world-sink`'s disc-4 step is the mirror, which copies the edit where disc 4's cell matches disc 1 and REPLAYS the sink
on disc 4's own ground where it differs (the whole edit, atomically). A draft cannot mirror: it has no bundles, so the
mirror logs NOT RUN there and the replay never fires. So the draft runs the replay's own call itself (disc 4,
`--skip-mirror`). On promote, the live mirror copies over it where the discs match and holds it where they differ,
so disc 4 ends as `world-sink` itself would leave it. A `[[sink]]` row composed INTO A DRAFT makes the same second
call (`sinkedit.is_draft`), so an opened recipe writes the draft the tab wrote. In game here, block (4,8) differs on
disc 4: the mirror held the whole edit ("NOT MIRRORED ... Disc 4 keeps its own ground there") and the promoted
disc-4 files are the draft's own disc-4 sink.

## Moving the river (`world-river --move-from`)

**Why a move, measured first.** `world-river` carries the stock river cluster onto an island it mints round it on open
ocean, placed by a whole-block shift (`--at DX,DZ`). The island's block rectangle fits 56 shifts on disc 1, which are
28 placements (the x-torus lists each twice). **Every one is already overridden in FF9CustomMap-world**, mostly by
its islands and by the river the rung-4 carry placed at 512,128. Once the river's own files are left out, exactly
one more is free: shift (8,-3), `--at 512,192`, one block north. So the tool is a MOVE, and on this folder it has
one destination, measured by both the conservative rectangle and the exact cells.

**`world-river --at NEW --move-from OLD` (one verb, not `--remove` then a run).** Check has to judge the new
placement while the old river still stands, and B1 refuses any placement that overlaps the verb's own deploy. So
the verb reads the old deploy's files from the folder's ledger (`deploy_ownership`, as `--remove` does) and leaves
them out of every occupancy read (the composition's B1, the stack read, `--at auto`). Every gate then judges the new
placement as if the old river were gone. Only when every gate is green and the stage is audited does
`remove_deploy` take the old river out; then the new one is promoted. A refused move changes nothing. A file on the
old cells that is not that deploy's is R1, and no deploy there is R0. `[[river]]` rows take `move_from` (the
recipe's row for a move), and `--report-json` writes the verdict the card reads.

**The card**, "Move the river", is the carry frame (`workspace/worldriver.py` over `world/riveredit.py`):
- It reads where the river stands in the draft (or the folder), from each file's LAST ledger row. A cell the move
  fills with the old river's very bytes reads as the new placement only: the ownership read accepts any row with a
  file's bytes, so it would claim both.
- A click picks the nearest placement the river fits. The ghost is the fragment's own stock triangles and the island's
  coast ring, moved by the shift.
- The preview marks a placement free or held (the river's own files never hold one), and names the free placements
  when you click where the river is now. A folder with no river gets the plain carry (`--at`).

**What the move needed underneath, found by building it.**
1. A DRAFT CARRIES DELETIONS. `draft.edits` listed only changed or added files, so a removal never reached the live
   folder. Now `draft.removals` lists them, `promote` deletes them (parked and ledgered) before it writes, `revert`
   restores them, and the caption counts them.
2. THE STACK READ LETS A DRAFT STAND IN FOR ITS SOURCE (`draft.stands_in_for`). The live folder's copy of a river the
   draft has moved must not refuse the draft's own move.
3. THE LEDGER TRAVELS WITH THE BYTES. Promote ledgered every file as `world-promote`, so a promoted river read as
   foreign to `world-river` and could never be moved or removed again. Now each file keeps the draft row's writer,
   with `via: world-promote` on the same row. The mirror runs under that writer, the draft takes the live ledger
   after a Promote, Revert re-ledgers the draft's own bytes, and Undo/Redo put the ledger back with the bytes.
4. THE RELABEL. A file the draft left byte-identical but gave another writer (a cell the moved river fills with the old
   one's very bytes) needs no write. It does need its ownership, and its disc-4 copy mirrored again, so Promote finds
   those files from the ledgers and re-ledgers them.
5. Sidecars (`Donor.txt`) are ledgered through Promote under part `Donor`, as the seam ledgers them.
6. A stale hint fixed: B1's way out named the NEW placement (`--remove --at 512,192`, where no river stands). It now
   names the deploy's own placement from the ledger, and offers `--move-from` too.
