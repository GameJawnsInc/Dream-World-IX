# ALGORITHM

PER-FRAME WORLD-MAP GROUND QUERY (controlled on-foot actor). Chain: w_frameUpdate -> w_movementUpdate (ff9.cs:3810) -> w_movementControl (ff9.cs:5187) -> w_movementRoundCheck (ff9.cs:5682) -> w_cellHit (ff9.cs:3304) -> w_nwpHit (ff9.cs:7296) -> WMBlock.Raycast (WMBlock.cs:137) -> WMPhysics (WMPhysics.cs). All quoted lines re-verified in source.

1. SPEED/HEADING: pad sets heading; XZSpeed = S(speed_move*moveSpeed>>12); on foot speed_move=112 -> 0.4375 units/tick (ff9.cs:6165, :1473, S() = x*0.00390625 at :2406). Tick runs beside world.OnUpdate20FPS (ff9.cs:3809), nominally 20 Hz.

2. DEFLECTION FAN: for rot = 0 deg, then +/-11.25, +/-22.5 ... +/-78.75 deg (for num3=0; num3<PsxRot(1024); num3+=PsxRot(128); +rot tried before -rot) run steps 3-11 per candidate; first fully-accepted candidate breaks the fan (ff9.cs:5552-5562, 5600).

3. CANDIDATE POINT: copy actor pos; x += rsin(heading+180deg+rot)*speed; z += rcos(...)*speed; y is KEPT at the actor's CURRENT y (ff9.cs:5687-5689). The query samples the NEW (x,z) at the OLD height.

4. CACHE SELECTION: cache = w_moveCHRCache[w_moveCHRStatus[controlledActor.index].cache] (ff9.cs:5686) -- an 11-slot array of 10-entry rings, keyed by a static 22-row table (rows 3-7 share slot 1, etc., ff9.cs:1769+). The controlled walk runs with IgnoreExceptions/CastRayFromSky/UseInfiniteRaycast all false; fly, NPC re-ground, init/warp, get-off and camera probes raise them in bracketed pairs (ff9.cs:5191-5193, 5607-5609, 4598, 3965, 2943, 5843).

Null block or !IsReady (not streamed) -> return height defaultHeight=0 with pno=-1, a MISS (ff9.cs:7305-7313, 1330).

A matching slot re-tests ONLY its cached (walkMeshIndex, triangleIndex) with a BARE ray-triangle test: NO 4078/4088/2040 mapid skip, NO up-facing normal filter, and acceptance is intersect result != 0 -- codes 2 (ray coplanar) and -1 (degenerate) count as hits with hit.point = (0,0,0) (WMBlock.cs:145-162, 217-236; WMPhysics.cs:50-69, 63). FIRST cached success WINS OUTRIGHT -- no other triangle in the block is tested, no height comparison, cache not rewritten (WMBlock.cs:155-160, 171 '!flag' guard).

FULL SCAN (only if every cache slot missed): iterate ActiveWalkMeshes (= Form1WalkMeshes or Form2WalkMeshes by block Form, WMBlock.cs:10-18) in REGISTRATION order -- Object, Terrain, volcano meshes, Beach1, Beach2, Stream, River, RiverJoint, Falls, Sea1..Sea6 (WMWorld.cs:588+, 748+, 848) -- and within each mesh iterate triangles i=0..N in flat-array order (WMPhysics.cs:13). Per triangle: (a) mapid = (Int32)tangents[triangles[i*3]].x; skip if mapid in {4078, 4088, 2040} unless IgnoreExceptions (WMPhysics.cs:15-20); (b) skip if dot(up, TriangleNormals[i]) <= 0.1 (faces steeper than ~84.3 deg from horizontal; TriangleNormals = normalized cross(v1-v0,v2-v0) computed at load in block-local space, WMBlock.cs:65-72) unless IgnoreExceptions (WMPhysics.cs:22-29); (c) world-transform the three verts via transform.TransformPoint (WMPhysics.cs:33-35); (d) plane-then-barycentric intersect accepting ONLY code 1 with t>=0 (WMPhysics.cs:37, 71-119). # REGIME_STOCK

STOCK: at every plan point of a block exactly ONE up-facing walk-class sheet passes the filters. Then first-in-order = only-hit = correct height, and the cache is a pure optimization: a cached triangle either still contains the plan point (same answer as the full scan would give) or geometrically misses (fall through to the full scan, which repopulates the ring). Hills walk correctly because each ~0.4375u step re-snaps y to the single surface, and the +2.34375 ray-origin allowance per step permits any stock grade (rise up to 2.34u per 0.44u advance). Mountains BLOCK through exactly two mechanisms, both functions of the destination probe (there is no lateral collision at all): (a) the probe hits a mountain-class triangle whose topograph bit is absent from the on-foot limit mask {0x0010667F,0xD8FF3CFF} -> mask reject at ff9.cs:5702/5726; or (b) the wall surface lies above origin (current_y+2.34375) so the down-ray cannot reach it, faces steeper than ~84 deg are filter-skipped anyway, and NOTHING walkable lies below -> pno=-1 miss reject at ff9.cs:5700. Both mechanisms depend on the invariant that no walkable sheet exists UNDER the wall: stock authors the world so a blocked plan point has either a blocking-class triangle or nothing at all beneath it. Under that contract every element of the algorithm -- first-hit-wins, unbounded drop, cache pinning, filter-free fast path -- is invisible.

# REGIME_OVERLAY

OVERLAY (carried mountain-skirt walk sheet laid OVER a continuous stock lawn; two stacked walk-class sheets everywhere in the footprint): the same code path now has two lawful answers at every plan point, and every observed symptom follows. (1) FIXED HEIGHT / WALKS THROUGH HILLS: once the actor is grounded at lawn height (it enters the footprint from the lawn), each frame's candidate probe origin is lawn_y+2.34375; any hill surface more than 2.34375 above is BEHIND the ray origin and mathematically unreachable (WMPhysics.cs:96 rejects t<0), while the lawn beneath always intersects. The lawn hit has a walkable topograph, passes the mask, the step is ACCEPTED and y snaps back to the lawn (ff9.cs:5698, 5718-5723) -- every frame. The cache reinforces it: the ring holds recently-walked lawn triangles, and the fast path returns the first cached intersection without testing anything else (WMBlock.cs:155-160), so even where the hill surface IS within reach, the lawn wins by history. (2) NOT BLOCKED BY THE MOUNTAIN: the wall-block mechanism is 'miss OR blocked-class hit' -- but here the probe under the wall always lawfully hits walkable lawn (unbounded drop, dead distance parameter), converting the stock miss-reject into an accept; steep wall faces are additionally invisible to the scan (dot(up,n)<=0.1 skip). Collision is not weakened -- it is bypassed wholesale (the FC-8 mechanism). (3) APPEARS ON THE ACTUAL GROUND NEAR CLIFFS: near the skirt margins the carried surface descends to within 2.34375 of the lawn, so BOTH sheets are inside the ray's reach and nearly coincide in height; whichever wins (by cache history or mesh/triangle order) yields approximately the true ground height, so the actor visually rides the real terrain there. The transition boundary between 'rides the skirt' and 'pinned to the lawn' is exactly the contour where carried_surface - lawn_y = 2.34375, modulated by ring history -- matching 'correct near cliffs, fixed-height inland'.

# REGIME_SHINGLE

SHINGLE (lawn tris wholly inside the footprint and below the carried surface deleted; boundary-CROSSING lawn tris kept whole, leaving under-lawn strips up to a full triangle ~4-6u inside the footprint): most of the footprint is now single-sheet, so the algorithm behaves as in stock -- 'mostly correct'. The residual defects are confined to the strips and are HISTORY-dependent, which is why the pattern is untrackable. At a strip plan point two sheets stack. (a) PHASE-INTO-GROUND: walking upslope onto a strip, the candidate probe can resolve to the kept lawn triangle -- guaranteed when the hill surface at the new (x,z) is >2.34375 above current y (hill behind origin, lawn the only reachable hit), and even when the hill IS reachable the lawn can still win via the cache ring (the actor just walked that boundary triangle, so it sits in the 10-slot ring and the fast path returns it before any scan, WMBlock.cs:147-160) or via triangle array order in the full scan (first-in-order, WMPhysics.cs:37). The unbounded down-snap (dead distance, ff9.cs:5720 'pos = vector' including y) then drops the actor to the lawn UNDER the hill surface -- phased into the ground. (b) MISSED HILLS: now lawn-pinned inside the strip, the hill above is >2.34375 up and unreachable; the actor traverses at lawn height until the strip ends. Past the strip the lawn is deleted: the next probe over the deleted region finds only hill triangles, all above origin -> pno=-1 -> mask of the fan deflections decides whether the actor stalls, slides along the strip edge, or re-grounds where the hill dips within reach -- entry angle, speed and ring contents determine which, hence 'some spots, untrackable'. The reported locus (434,-542) maps to block col=(Int32)(434/64)=6, row=(Int32)(542/64)=8 (WMWorld.cs:329-330) -- a place where boundary-crossing tris were kept, i.e. a DATA locus, not a code special case. The intended 1.2u margin is irrelevant to the engine: any strip penetration deeper than 0 combined with a >2.34375 hill-lawn gap reproduces the defect; strips up to 4-6u guarantee whole plan points where the lawn is the only reachable or cache-preferred answer.

# INVARIANTS

- SINGLE-REACHABLE-SHEET: at any plan point (x,z), among triangles passing the full-scan filters (mapid not in {4078,4088,2040}, faceNormal.y > 0.1), at most ONE intersects the downward vertical line at or below actor_y + 2.34375. If two do, the returned height is mesh-order/triangle-order/cache-history dependent, never 'topmost'.
- SINGLE-SHEET-AT-ANY-DEPTH (strong form, required for cache neutrality): at any plan point, ALL up-facing walk triangles on the vertical line lie on one surface. Because the cast is unbounded downward (dead distance parameter) and any accepted hit snaps y with no descent limit, a second sheet at ANY depth below is reachable and eligible to win.
- WALL CONTRACT: an impassable boundary exists at a plan point only if EITHER (a) the first-in-order reachable triangle there has a topograph outside the transport's limit mask, OR (b) NO filter-passing walk triangle exists at or below actor_y + 2.34375 there. A walkable-class triangle at any depth below the point legalizes the step and dissolves the wall.
- CLIMB CONTRACT: a surface is reachable on foot only through a chain of plan points where each successive surface height <= previous surface height + 2.34375 (evaluated per ~0.4375u step); ascent steeper than that is a permanent miss, descent of any magnitude is accepted in one step.
- ORDER CONTRACT: where sheets overlap in plan, the intended winner must precede the other in ActiveWalkMeshes registration order (Object -> Terrain -> water set) and, within a mesh, in flat triangle-array order; an offline simulator must replicate exact emit order to be predictive.
- CACHE NEUTRALITY: the 10-slot per-actor ring (probed newest-first, first intersection wins outright, bypassing the mapid skip-list and the normal filter, accepting intersect codes 2 and -1) is a pure optimization ONLY under the strong single-sheet invariant; violated, ring history becomes hidden game state with no invalidation ever (process-lifetime caches; Form switches and block streaming reloads do not clear it).
- MESH SHAPE: walk meshes are non-indexed triangle soup (vertices.Length == triangles.Length), tangent.x of a triangle's FIRST corner carries its 16-bit IDALL (bits 15-14 event, 13-8 area, 7-2 topograph); TriangleNormals are geometric winding normals computed in block-local space, correct against world-up only for translation-only block transforms.
- BLOCK OWNERSHIP: a triangle answers queries only for plan points inside the 64x64 footprint of the block that OWNS it in its mesh list -- there is no neighbor fallback and no clipping; a not-yet-streamed (!IsReady) or off-grid block answers height 0 / miss.
- TOPOGRAPH SEMANTICS: acceptance is purely the 64-bit limit-mask membership of bits 7-2 of the hit IDALL (on foot {0x0010667F, 0xD8FF3CFF}); no slope, no y-delta, and no lateral test exists anywhere in the walk loop.

# GAPS

- MESH/TRIANGLE ORDER OF OUR DEPLOYED BLOCKS: which sheet wins a full scan in overlap regions depends on the exact registration order and flat triangle emit order of the minted .ff9mesh (loose-override path WMWorld.cs:823+ replaces both render and walk mesh). The source fixes the FRAMEWORK order (Object before Terrain before water) but not the order inside our carried/skirt meshes. The bench simulator is uncalibrated until it replicates the actual deployed byte order -- follow-up against the ff9mapkit emitters, not this source.
- OVERLAY 'appears on the actual ground near cliffs' has two candidate sub-mechanisms consistent with the model -- (a) both sheets within 2.34375 so either winner looks correct, (b) the carried mesh genuinely winning by order/cache at the margins -- distinguishing them needs the deployed mesh order or an instrumented probe log, not more source reading.
- PSX FIDELITY OF THE DEAD DISTANCE: whether original PSX FF9 enforced the finite 2.8-unit ray (capping descent at ~0.46 below feet) cannot be settled from this decompile; if it did, Memoria's unbounded drop is a port divergence and the 'any-depth snap' is Unity-era behavior.
- SEMANTICS OF THE EXCEPTION MAPIDS: 4078 (0xFEE), 4088 (0xFF8), 2040 (0x7F8) skipped in the full scan, and 0x31EE (12782) flight-only -- their in-game meaning is data-side (stock tangent-channel census needed); the 0xFEE-family sentinel remaps at ff9.cs:5209-5233 suggest scripted/vehicle-parking surfaces but this is inference.
- CONTROLLED ACTOR'S CACHE SLOT: w_movementRoundCheck indexes w_moveCHRCache by w_moveCHRStatus[controlledActor.index].cache with NO guard against the value 10 (the 'skip height' marker row value); which row index the controlled actor occupies in each control mode (and whether slot 10 is ever used as a real ring) was not mapped -- matters for simulating ring sharing.
- FORM1/FORM2 LIST LENGTH PARITY: a cached WalkMeshIndex minted under one form indexes the other form's list after an event-driven SetForm flip with no invalidation; walkMeshes[walkMeshIndex] at WMBlock.cs:219 would throw if lengths differ. Code hazard confirmed; whether shipping/minted data ever has unequal per-form list lengths is unverified.
- BLOCK TRANSFORM ASSUMPTION: TriangleNormals are computed in block-LOCAL space but dotted against world up, while intersection verts are world-transformed -- correct only if block transforms are translation-only. Block placement code (rotation/scale never applied) was not exhaustively proven.
- TRANSPORTCONTROLS.CSV AT RUNTIME: Memoria's PatchWorldCHRControl can wholesale-replace w_moveCHRControl including every limit mask (WorldConfiguration.cs:134); whether THIS build ships a CSV that actually overrides the hardcoded on-foot mask at runtime was not traced to the load call site -- the simulator should read the live CSV if present.
- TICK CADENCE: w_movementUpdate runs beside world.OnUpdate20FPS (ff9.cs:3809) implying 20 Hz sim (foot speed 8.75 u/s), but the w_frameUpdate caller cadence up to the Unity loop, and Memoria.SmoothFrameUpdater_World's visual interpolation, were not traced; they affect only visual smoothing, not the query math.
- CROSS-BLOCK OVERHANG in stock/minted data: the code neither clips triangles to the 64-unit tile nor tests neighbors, so a triangle overhanging its owner block's footprint is invisible to queries made from the neighboring block (height 0/miss). Whether stock or our minted walkmeshes duplicate border triangles into both blocks is a byte-level data question.
- CurrentX/CurrentY INITIAL ESTABLISHMENT: SwapBlock provably preserves the Blocks[i,j].Current==(i,j) invariant but the establishing write (prefab bake / BuildBlockArray path) was not located; if a prefab shipped Current!=Initial the GetAbsoluteBlock double-lookup would stop being an identity.
- REGIME CALIBRATION CAVEAT: all three regimes ARE mechanically produced by the same code path, but the shingle regime's per-spot outcome is genuinely non-deterministic from position alone (ring history + entry trajectory + triangle order); the model predicts the CLASS of defect and its locus (strip footprints), not a per-frame reproduction without simulating the ring.

## FC-8 [high] HOW A WALL BLOCKS — and why a second ground sheet bypasses it
The world map has NO lateral/swept collision at all; a 'wall' blocks only through the destination down-probe, via two stock mechanisms: (a) TOPOGRAPH HIT — the probe hits a mountain-class triangle at the destination (its topograph bit absent from limit) and the move is rejected at ff9.cs:5702/5726; (b) MISS — the wall surface at the destination x/z lies ABOVE the ray origin (feet+2.34375) so a downward ray cannot reach it, and faces steeper than ~84 deg are invisible to the scan anyway; with nothing else below, pno stays -1 and 5700 rejects. Adding a WALKABLE ground sheet UNDER the wall converts mechanism (b) into a lawful hit: the ray falls past the unreachable/skipped wall triangles, hits the sheet (unbounded drop, FC-5), the topograph passes the on-foot mask, and w_movementRoundCheck returns true with y snapped to the sheet — the actor walks straight through the mountain. The triangle cache makes this WORSE: WMBlock.Raycast tests the actor's 10 cached (previously-walked ground-sheet) triangles FIRST and returns on the first cache hit, so a blocking wall-foot triangle that would have answered in the full scan is never even tested. This is the exact source-level account of the playtest's 'no collision against the mountain when a second ground sheet lay underneath'.

# OPEN QUESTIONS

- Where is the raycast 'distance' actually enforced, if ever? WMBlock.Raycast's distance parameter is dead, and intersect3D_RayTriangle has no max-t test -- the ff9.cs callers (w_nwpHit at :7296, w_nwpHitBool at :7326) must be read to see whether they compare hit.point against origin post-hoc or whether the finite ray length is purely notional.
- Do WMBlock transforms ever carry rotation or non-unit scale? TriangleNormals are computed in block-LOCAL space but the up-facing filter dots them against world up, and the intersection triangle IS world-transformed via TransformPoint -- the filter is only correct if block transforms are translation-only (PositionAsCenter suggests they are, but this was not proven from the block-placement code).
- Can a cache entry written during an IgnoreExceptions=true window (e.g. the fly-path at ff9.cs:5191-5193) later validate hits on a 4078/4088/2040-mapid or downward-facing triangle after the flag is cleared? The cached RaycastOnSpecifiedTriangle path applies no filters, so a stale cache slot bypasses the skip-list entirely -- only the 0x31EE veto survives.
- What do mapids 4078, 4088, 2040, and 0x31EE (12782) mean semantically, and what is w_moveCHRControlPtr.type == 1 (which exempts an actor from the 0x31EE veto)? Neither is decodable from the WM layer alone; the ff9.cs movement tables own it.
- Is the != 0 acceptance in RaycastOnSpecifiedTriangle (admitting ray-in-plane code 2 and degenerate code -1 with hit.point = Vector3.zero) intentional stock behavior or a latent quirk? A cached degenerate/coplanar triangle would report a hit at the world origin; no caller-side guard against point == zero was seen in the files read.
- Do stock (or minted) walkmesh meshes ever contain triangles overhanging their 64-unit tile? The code neither clips nor tests neighbors (BL-4), so this is a data question: if border triangles are duplicated into both blocks the single-block query is safe; if not, positions over an overhang read height 0. Needs a byte-level check of adjacent blocks' shared-edge triangles.
- Where are CurrentX/CurrentY first initialized to equal the block's starting slot? The SwapBlock invariant (BL-2) preserves it, but the establishing write (prefab bake via WMWorldPrefabMaker or scene data) was not located in the files read; if a prefab ships CurrentX!=InitialX the GetAbsoluteBlock double-lookup would matter.
- Semantics of the special mapids: 0x31EE (=12782, hit only for transport type 1 = flight) and the excluded trio 4078/4088/2040 in WMPhysics.Raycast. These are data-side topograph codes; their in-game meaning (chasm? Hilda Garde landing? scripted zones?) is not derivable from these files.
- OnObject in s_moveCHRCache is read at WMBlock.cs:154 but only ever written 0 (flag3 is forced false before the sole write at :178, and no other writer exists in Global). Is this a vestige of a removed object-raycast path (the flag3 dataflow suggests hits on 'object' meshes were once cached distinctly)?
- WMPhysics.IgnoreExceptions / CastRayFromSky / UseInfiniteRaycast are global mutable statics; which code paths toggle them (and whether IgnoreExceptions can be true while a cache is being populated, arming the BL-10 stale-wall-hit hazard) was not traced -- they live in the movement layer (ff9.cs), outside this subsystem.
- The fast path accepts intersect3D_RayTriangle results -1 (degenerate) and 2 (ray in plane) with hit.point = Vector3.zero (BL-10). Can a degenerate triangle actually enter the cache?
